### 1. 单据模型改造

`purchase_orders` / `sales_orders` 各从 6 列扩到 22 列：

| 分组      | 字段                                                                                                                              |
| ------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 单据头     | warehouse_id 仓库、businesser 业务员、order_date 开单日期、delivery_date 送货日期、payment_method 付款方式、contact / contact_phone / address 快照、note |
| **结算链** | payable_amount(应收 receivable_amount) → discount_amount 优惠 → paid_amount(实收 received_amount)                                     |
| **欠款链** | current_debt 本次欠款 → prev_debt 前次欠款 → total_debt 累欠货款                                                                            |
| 其他      | is_invoiced 是否开票                                                                                                                |

**实付/实收金额不填 = 0（本单全额挂账）**。这是刻意的会计选择：宁可高估应付，不可高估已付，  
否则对账单上永远没有真实的往来发生额。收款/付款由「收款登记 / 付款登记」逐笔冲减。

### 2. 单号自动生成

`_next_doc_no()`：`前缀 + YYYYMMDD + 3 位流水`，当天同前缀取最大值 +1。

- 采购入库：`CG20261010001`
- 销售开单：`XS20261010001`

### 补充改造：解除列表接口数量限制（2026-10-10）

**问题**：12 个列表接口写死了 `limit` 默认值（100，发票是 500）。库里有 384 个商品时，  
界面最多只能看到 100 个 —— 静默丢数据。而且一旦记录数超过分页上限，  
测试里 `params={"limit": 500}` 这类断言就会不稳定。

**改法**：新增 `_paginate(query, skip, limit)` 统一分页助手，12 个接口签名改为  
`limit: int | None = None`：

- 不传 `limit` → 返回**全部**记录（新默认，永不截断）
- 传 `limit` / `skip` → 仍按老用法分页
- `limit=0` 或负数 → 等同全量

涉及接口：products / customers / suppliers / warehouses / purchase-orders / sales-orders /  
inventory / finance / invoices / production-boms / production-orders / projects + auth 的 users。

**实测**：商品 392 条全量返回（此前只能看到 100 条）；`?limit=10` 仍返回 10 条；  
`?skip=5&limit=3` 仍返回 3 条。66 个测试全过。

### 补充改造：档案删除接口（2026-10-10 21:15）

**背景**：发票 / 销售单 / BOM 都能删，但三类主数据档案（商品 / 客户 / 供应商）只有  
「列表 + 新建」，录错的档案删不掉，只能一直堆在库里。

**新增 9 个接口**（`app/api/v1/routes/erp.py`，纯新增 209 行，零修改零删除）：

| 方法         | 路径                           | 说明                     |
| ---------- | ---------------------------- | ---------------------- |
| GET        | `/customers/{id}/references` | 删前预览：该档案被哪些业务数据引用、各多少条 |
| DELETE     | `/customers/batch`           | 批量删除，逐条判定，不整批失败        |
| DELETE     | `/customers/{id}`            | 单条删除 → 204             |
| GET/DELETE | `/suppliers/...`             | 同上三个                   |
| GET/DELETE | `/products/...`              | 同上三个                   |

路由顺序：`/batch` 必须注册在 `/{id}` 之前，否则 `batch` 会被当成 id 报 422（同 invoices）。

**核心设计 —— 引用检查 + 强制删除**

档案是主数据，单据是业务数据。直接删档案会让单据指向一个不存在的对象  
（列表里客户名变空白）。所以默认先查引用：

- **没被引用** → 直接删除。录错的档案都属于这一类。
- **已被引用** → 返回 **409**，detail 写明「客户「张三（C-001）」已被 销售单 1 条、  
  财务流水 1 条 引用，无法删除。请先处理相关业务数据，或带 force=true 强制删除。」
- 带 `?force=true` → 强制删除档案本身，**不动业务单据**。因为第 2 步已给单据明细  
  存了 `product_name` / `standards` / `unit` 快照，历史单据的打印与金额不受影响。

引用检查覆盖范围：

| 档案  | 检查的业务数据                                 |
| --- | --------------------------------------- |
| 商品  | 采购单明细、销售单明细、库存流水、生产BOM（母件+子件）、生产工单、财务流水 |
| 客户  | 销售单、财务流水                                |
| 供应商 | 采购单、财务流水                                |

**前端入口**（`frontend/src/App.jsx` + `styles.css`）：

- 商品 / 客户 / 供应商列表每行加「删除」按钮，复用已有的删除确认弹窗
- 若后端返回 409，弹窗自动切换成「强制删除」二次确认，把后端的引用说明原样展示
- **同时解除这三张列表「只显示最近 8 条」的渲染限制**（原 `slice(0, 8)`）——  
  此前即使有删除按钮，也只能删到最近 8 条

导入语义：

- `mode=upsert`（默认）已存在编码 → **更新**；`mode=skip` → 跳过

- `dry_run=true` **只校验不落库**，供前端「预检」
- **每行一个 SAVEPOINT**（`db.begin_nested()`）—— 单行失败只回滚该行，其他行照常提交
- 返回 `{parsed, created, updated, skipped, failed, errors[]}`

中文文件名下载用 RFC 5987（`filename*=UTF-8''…`）+ ASCII 兜底，避免 HTTP 头编码问题。

## 第 3.5 步之十：购销合同 A2 · 标准版（2026-10-10）

**目标**：用户最初说"软件里的合同模板不满意"，本次按《单据模板选型清单》的 **A2 购销合同·标准版**  
（常规采购/销售，含验收与付款节点，2-3 页）落地：新建合同数据模型 + 录入界面 + 后端直出 PDF。

### 一、数据模型（新增 `app/models/contract.py`）

| 表                | 说明                                                             |
| ---------------- | -------------------------------------------------------------- |
| `contracts`      | 合同主表：编号/模板/类型/状态、甲乙方快照（9+8 字段）、签订与有效期、金额与结算、A2 条款变量（12 个）、关联单据 |
| `contract_items` | 标的物清单：商品快照（名称/规格/单位）+ 数量/单价/金额                                 |

**三条设计口径（写进模型注释，避免以后被人改坏）**：

1. **合同不写财务流水** —— 合同是意向性文件，会计上不能凭一纸合同确认应收应付，否则报表立刻虚增。
2. **与财务/库存的关联靠「一键转单」** —— `POST /contracts/{id}/to-order` 把合同生成正式  
   采购单/销售单，由单据去联动库存与财务（单据备注带 `由合同 HTxxx 生成`，可溯源）。  
   `DOC_TYPES` 里登记了 `contract: 购销合同`，保持"财务 × 全模块关联"的口径完整。
3. **甲乙方信息创建时快照** —— 合同是法律文件，不能让"客户改了地址"把三年前的合同一起改掉。

### 二、A2 条款框架（在 `erp.py` 的 `_a2_paragraphs()`，不在模型里存整段文字）

模型只存**变量占位**（质量标准、包装标准、交货方式、运输与风险、验收期限、异议期限、质保、  
付款节点、开票要求、违约金日利率、争议解决、份数、送达地址、补充条款），条文框架由后端生成：

```
第一条 合同标的      第二条 质量标准     第三条 交付与运输   第四条 包装
第五条 验收          第六条 质保与售后   第七条 价款支付与发票
第八条 违约责任      第九条 不可抗力     第十条 争议解决     第十一条 其他约定
（填了补充条款则追加 第十二条 补充约定）
```

- 变量留空由 `_A2_DEFAULTS` 兜底（行业常规表述），**保证打印出来是一份完整可用的合同**，不是一堆空白占位。
- 违约金按「万分之几」在界面填写，落库存日利率小数（0.0005 = 万分之五）。
- 甲乙方角色随类型互换：销售合同我方是乙方（供方），采购合同我方是甲方（需方）。
- 我方抬头信息读环境变量 `ERP_COMPANY_NAME / ERP_COMPANY_TAX_NO / ERP_COMPANY_LEGAL /
  ERP_COMPANY_ADDRESS / ERP_COMPANY_CONTACT / ERP_COMPANY_PHONE / ERP_COMPANY_BANK /
  ERP_COMPANY_ACCOUNT`，不把公司信息写死在代码里。

### 三、接口（10 条）

| 方法     | 路径                           | 说明                                                                      |
| ------ | ---------------------------- | ----------------------------------------------------------------------- |
| GET    | `/contracts/meta`            | 字典：模板/类型/状态/条款默认值/我方默认主体                                                |
| GET    | `/contracts`                 | 列表（`contract_type` / `status` / `party_id` / `keyword` 过滤，不传 limit 即全量） |
| POST   | `/contracts`                 | 新建（自动单号 `HT+日期+3位流水`、明细快照、金额大写、条款兜底）                                    |

转单的边界：没关联档案（只有对方名称）或没有明细时返回 400；已转单过再转返回 409。

### 四、打印

合同模板走既有 `pdf_render.render_document_pdf()`：抬头/副标题（模板版本）/右上合同编号、

`/print/{doc_type}/{doc_id}` 是通配路由且注册在前，单独挂 `/print/contract/{id}` 会被它先吃掉（返回 404）。

## 第 3.5 步之十七：采购退货（第 2 批 · 第 2 个单据表）

> 第 2 批第 2 项。采购退货是采购入库的**反向**单据：货退回给供应商，  
> 库存减少、应付冲减。与报价单（商务意向、不碰库存财务）不同，退货是**真实单据**。

### 一、数据模型（纯新增表，不动既有表）

- 新建 `app/models/purchase_return.py`：
  - `purchase_returns`：退货单号、供应商 id + 快照（名称/联系人/电话/地址）、退货仓库、业务员、

## 第十步：库存调拨（第 2 批 · 第 4 个单据表）

> 2026-10-13 | 对齐浩技云「库存管理 → 调拨管理」

### 一、为什么调拨要独立成表、却**不写财务流水**

调拨与退货都是一张新单据表，但财务口径完全相反：

| | 采购/销售退货 | **库存调拨** |
|---|---|---|
| 方向 | 与出/入库相反（反向单据） | **企业内部位置转移** |
| 总量 | 变（退货改变总量） | **不变** |
| 库存流水 | 一条（inbound 或 outbound） | **两条**（调出 outbound + 调入 inbound） |
| 财务流水 | 写（冲减应付/应收） | **不写** |

调拨是货从 A 仓搬到 B 仓，资产总额没变、往来账没动，按行业标准做法
**只记库存、不记财务**。`DOC_TYPES.inv_transfer` 只用于库存流水溯源与
「变动查询」归类，不产生任何 `financial_transactions` 记录 —— 这一点在测试里
用**反向断言**锁死（`assert not any(row.related_type == "inv_transfer")`），
避免以后有人"顺手"补一条财务流水。

### 二、做了什么

| 表 | `app/models/inventory_transfer.py` | `inventory_transfers`（调出/调入仓库、日期、经办人、原因、总数量、状态）+ `inventory_transfer_items`（商品快照 + 数量 + 成本单价） |
| 字典 | 模型内 `TRANSFER_STATUS` | draft 草稿 / submitted 已调拨 / cancelled 已取消 |
| 接口 | `app/api/v1/routes/erp.py` | **8 条**：meta / 列表 / 详情 / 新建 / PATCH / PATCH status / DELETE / 打印；单号前缀 **`DBD`** |

### 三、三条关键设计（都是被业务逼出来的）

1. **调出仓库 ≠ 调入仓库**，前后端双重拦截。后端 `_validate_transfer_warehouses`
   返回 400/404；前端在选完调出仓后把它的选项从调入仓下拉里剔除，并自动清空已选的同仓。
2. **删单一次冲销两条流水**。两条流水共用 `related_type="inv_transfer"` +
   `related_order_id`，`_revert_stock` 一把全删 → 调出仓加回来、调入仓减回去，
   两侧同时复原（验证实测 7480/5720 → 7477/5723 → 7480/5720）。
3. **PATCH 改明细/改仓库时整体重放库存**。这是与销售退货实现的一个刻意区别：
   退货改明细只重算金额（不动库存），而调拨改数量必须先 `_revert_stock` 再
   `_transfer_apply_stock`，否则会出现「调出减了、调入没加」的单边账。
   验证里把数量从 3 改成 8，流水仍是 2 条（不累积），库存精确变为 -8/+8。

## 第十一步：库存盘点（第 2 批 · 第 5 个单据表）

> 2026-10-13 | 对齐浩技云「库存管理 → 盘点管理」

### 一、盘点与其他单据的根本区别：账面数不是人填的

调拨、退货、报损的明细都要人一行行录；**盘点不是**。盘点的「账面数」必须是
系统按现存量算出来的，人只负责填「实盘数」，差额才是盈亏。所以这次新增了一个
其他单据都没有的接口：

```
GET /stocktakings/plan?warehouse_id=204
→ { warehouse_name: "寨卡仓库", count: 19, rows: [{product_name, book_quantity, unit_price, ...}] }
```

前端点「带出账面库存」即调它生成盘点底稿（默认实盘数 = 账面数，只改有差异的行）。
界面实测：寨卡仓库一次带出 **19 行**，首行「劳保手套」账面 7480。

### 二、盈亏方向由**明细行自己**决定

一张盘点单会同时产生两类流水 —— 盘盈的行走 inbound、盘亏的行走 outbound，
两条共用 `related_type="inv_check"` + 本单 id，删单时 `_revert_stock` 一次全冲。
验证里刻意造了一张**同时含盘盈与盘亏**的单：盘盈商品 10 → 14、盘亏商品 10 → 6，
两条流水类型正好 `["inbound", "outbound"]`。

`diff_quantity = actual_quantity - book_quantity` **由后端统一计算**，前端不许自己算 ——
口径一旦分叉，库存就烂了。

### 三、做了什么

| 层 | 落点 | 内容 |
|---|---|---|
| 表 | `app/models/stocktaking.py` | `stocktakings`（仓库、日期、盘点人、范围、**盘盈量/盘亏量/盈亏行数分开记**、盈亏金额净额、状态）+ `stocktaking_items`（账面/实盘/盈亏/成本价） |
| 字典 | 模型内 `STOCKTAKING_STATUS` | draft 草稿 / submitted 已调整 / cancelled 已取消 |
| 接口 | `erp.py` | **9 条**：meta / **plan（盘点底稿）** / 列表 / 详情 / 新建 / PATCH / status / DELETE / 打印；单号前缀 **`PD`** |
| 打印 | `_PRINT_KINDS["stocktaking"]` | 「库存盘点单」，列 = 序号/商品/规格/单位/**账面数/实盘数/盈亏**/备注 |
| 页面 | `App.jsx` | 菜单 `stocktaking` 摘掉 `todo`；左表单（双列头 + 「带出账面库存 / 手工加行」）+ 明细表 + 列表 |

盘盈量与盘亏量**分开记**（`total_profit` / `total_loss`），不做净额抵消 ——
净额会把「盘盈 4 件、盘亏 4 件」显示成 0，问题被藏起来。

### 四、与调拨一致的纯库存口径

盘点**只写库存流水、不写财务流水**（盘盈盘亏的账务处理走「日常收支」，系统不擅自记账），
测试里用反向断言锁死：

```python
assert not any(row.get("related_type") == "inv_check" for row in fin)
```

### 五、第 2 批的代码复用情况

第 4 个单据表（调拨）沉淀下来的三样东西，在盘点里**原样复用**：

1. `_revert_stock` + 整体重放的 PATCH 写法 —— 改明细先冲销再重放，避免单边账；
2. 前端 `stockByWarehouseProduct`（仓库 × 商品索引）—— 明细行内显示该仓现存；
3. `jumpToStock` —— 「查库存」跳转。

## 第十二步：报损报溢（第 2 批 · 第 6 个单据表）

> 2026-10-13 | 对齐浩技云「库存管理 → 报损报溢」

### 一、为什么报损报溢是**一张表**，退货却是两张

| | 采购/销售退货 | **报损 / 报溢** |
|---|---|---|
| 字段结构 | 完全不同（供应商+应付 vs 客户+应收） | **完全对称**（仓库+数量+成本价） |
| 方向差异 | 涉及往来单位，业务语义分家 | **只有库存方向相反** |
| 落库 | 拆成 `purchase_returns` / `sales_returns` | **合表** `inventory_adjustments` + `adjust_type` |

方向差异用一个字典表达，业务代码不写 `if`：

```python
ADJUST_TYPES = {
    "scrap":    {"label": "报损", "direction": "outbound", "prefix": "BS", "doc_type": "inv_scrap"},
    "overflow": {"label": "报溢", "direction": "inbound",  "prefix": "BY", "doc_type": "inv_overflow"},
}
```

单号前缀也随之分家：报损 **`BS`**、报溢 **`BY`**，两类单号各排各的号。

### 二、明细数量恒正

业务填「坏了 3 件」，不是「-3 件」。后端对明细数量取绝对值（`abs()`），
方向完全由单据头决定 —— 避免同一张单里正负混排、也避免一张报损单里混进一行盘盈。
测试专门验证：传 `quantity: -5` 仍按 **5 件**记录，库存 10 → 5。

### 三、改类型 = 改方向，必须整体重放

`PATCH /inventory-adjustments/{id}` 传 `adjust_type` 时，先按**新旧两个 doc_type
各冲销一次**（幂等且安全），再按新方向重放。测试验证「报损改报溢」：
库存 10 → 8（报损 2）→ **12**（冲回 2 再报溢 2），账面只留 1 条 inbound 流水。

### 四、纯库存口径 + 打印分家

- 不写财务流水（与调拨、盘点一致），反向断言锁死；
- 打印登记两条：`_PRINT_KINDS["inventory-scrap"]`（库存报损单）、
  `_PRINT_KINDS["inventory-overflow"]`（库存报溢单），共用 `_adjust_print_spec`，
  只在标题/原因标签/库存方向三处按类型切换。

### 五、界面上的类型切换

页面顶部两枚方向卡（`.type-switch-btn`）——「报损 / 减少库存」「报溢 / 增加库存」，
选中态用蓝色描边。切换类型时**表单标题、字段标签、按钮文案、提交后的提示语**
全部跟着变（`adjustTypeLabel()` / `ADJUST_TYPE_DIRECTION`）。

## 第十三步：第 3 批 · 生产类（生产计划 → MRP → 领料 → 退料 → 成品入库 → 委外加工）

第 3 批把「排产 → 物料需求 → 领料 → 退料 → 成品交库 → 委外收发」整条生产链路打通，
共 6 个模块、5 张新单据表 + 1 个运算引擎。核心设计是**三层单据口径**：

| 口径 | 单据 | 库存 | 财务 |
|---|---|---|---|
| 前置单据（排产意图） | 生产计划、MRP 运算 | ✗ 不写 | ✗ 不写 |
| 纯库存单据 | 生产领料、生产退料 | ✓ 写 | ✗ 不写 |
| 库存 + 财务双动单据 | 成品入库、委外加工 | ✓ 写 | ✓ 写 |

每层都用**反向断言**锁死：测试先记 `len(inventory) / len(finance)`，建单后断言长度
变化符合该层口径 —— 前置单据前后不变，纯库存单据只涨库存不涨财务。

### 13.1 生产计划（第 3 批 · 第 1 个单据表）

- 模型 `app/models/production_plan.py`：`production_plans` + `production_plan_items`。
  计划类型 `self`（自制，单号 **SCJH**）/ `outsource`（委外，单号 **WWJH**）。
- **前置单据**：写库只管"要排什么产"，**不写库存、不写财务**（与报价单同模式）。
- 关联来源 `source_order_id / source_order_no` 预留销售订单转生产计划。
- 接口 8 条（meta/列表/详情/POST/PATCH/status/DELETE/打印）；
  DELETE 带**下游引用拦截**：被领料 / 退料 / 成品入库引用时返回 409。
- 状态：`draft 草稿 / planned 已计划 / released 已下达 / closed 已关闭 / cancelled 已取消`。

### 13.2 MRP 物料需求运算（第 3 批 · 运算引擎）

- 按 `production_boms`（parent_id 自引用树）**逐层展开**：
  - 行 = `product_id`（由 `component_product_id` 组成、`quantity` 单位用量）
  - 毛需求 = 需求量 × 单位用量；净需求 = max(0, 毛需求 − 现存量)
  - **顶层成品是产出，不做缺料判定**（状态标 `product 产出`）
- 引擎函数：`_bom_children_map` / `_on_hand_by_product` / `_mrp_explode` / `_parse_mrp_demands`。
- 接口 3 条：`GET /mrp/requirements`、`POST /mrp/run`、`GET /production-plans/{id}/mrp`。
- 前端「MRP 运算」页支持：手填需求，或**从生产计划列表一键跳页带出计划**；
  结果按层显示，命中缺料时高亮并汇总「缺料金额」。
- 实测：成品×10 需原料 30、现存 5 → **净需求 25、缺料金额 ¥100**。

### 13.3 生产领料 / 13.4 生产退料（第 3 批 · 纯库存单据）

- `app/models/material_issue.py`（单号 **SCLL**）、`app/models/material_return.py`（单号 **SCTL**）。
- 领料 = 原料从仓库发到车间，**outbound**（`related_type="production_issue"`）；
  退料是领料的反向，余料退回仓库，**inbound**（`related_type="production_return"`）。
- 两者都是**纯库存单据**：只写库存流水、**不写财务**（材料成本归集落在下游成品入库）。
- 领料页有 `GET /material-issues/suggestion?plan_id=`：按生产计划**带出 BOM 展开底稿**，
  人不用一行行敲材料（与盘点带账面数同理）。
- 状态：领料 `draft/submitted已领料/cancelled`，退料 `draft/submitted已退料/cancelled`。

### 13.5 成品入库（第 3 批 · 收口环节，库存 + 财务双动）

- `app/models/finished_goods.py`：单号 **CPRK**，状态 `draft/submitted已入库/cancelled`。
- 车间把成品交回仓库：成品现存量**增加**（inbound，`related_type="production_in"`）。
- **同时写财务成本流水**：`transaction_type="cost"`、`direction="in"` ——
  这是"在制品 → 产成品"的价值结转；用 `cost` 类型**不影响应收应付余额**，
  只进成本口径报表。金额为 0 时跳过（不写空流水）。
- 可关联生产计划（`plan_id`），形成 计划 → 领料 → 退料 → 成品入库 的完整闭环。

### 13.6 委外加工（第 3 批 · 收官，库存 + 财务双动）

- `app/models/outsourcing.py`：单号 **WWJG**，状态 `draft/submitted已收发/cancelled`。
- **一张单两个方向**：
  - 发出材料（`outsourcing_items` 明细）→ 原材料 **outbound**
  - 收回成品（单据头 `product_id + quantity`）→ 成品 **inbound**
  - 两类流水共用 `related_type="outsourcing"` + 本单 id，**删单一次全冲**。
- 与自制不同，委外要**付加工费**：单据头 `process_fee` 审核后产生**应付**
  （`transaction_type="payable"`、`direction="out"`，挂外协厂 `supplier_id`）。

## 第十五步：第 4 批 · 报表中心 16 张（2026-10-13）

浩技云的「报表」分组有 16 页，方案文档里标的是清一色 🔵（*现有数据聚合即可*）。
这一批就是把那 16 张补齐。

### 15.1 为什么不塞进 erp.py，而是新开一个模块

erp.py 已经 9300+ 行 —— 它是**所有业务单据**的家。报表是另一种东西：

- 没有单据生命周期（不草稿、不提交、不删除）；
- 不联动库存、不写财务、没有打印注册与 Excel 注册表；
- 天然需要自己的引擎（分桶、维表、交叉表），和单据代码**没有共享函数**。

所以新开 `app/api/v1/routes/reports.py`，挂在 `/reports` 下，在
`app/api/v1/router.py` 注册。**这是本项目第一次把业务代码拆出 erp.py**，
理由写在这儿免得后人以为是随手拆的。

### 15.2 16 张报表其实只有四种「形状」

| 形态 | 张数 | 报表 | 说明 |
|---|---|---|---|
| `crosstab` 交叉表 | 13 | 商品/客户/商品分类 的 日/月/季/年 报（12 张）+ 销售员报表 | 行 = 维度实体，列 = 期间桶，格 = 数量/金额 |
| `detail` 明细表 | 1 | 商品销售明细表 | 原始单据行，不聚合 |
| `flow` 收发存 | 1 | 商品出入统计 | 期初 + 入库 − 出库 = 期末 |
| `overview` 大盘 | 1 | 老板报表 | 收入/成本/毛利/应收/应付/库存 + 四张 Top5 |

前 12 张**只差两个参数**（`dimension` × `period`），所以共用一个聚合引擎：
先在库端按日期取一次销售事实，再在 Python 端按「维度 × 期间桶」分桶。
**一次查询喂 12 张报表**，不做 12 次全表扫。

### 15.3 接口只有 3 条（不是 16 条）

```
GET /reports/catalog              报表目录（16 张的元数据 + 维度/粒度字典）—— 唯一事实来源
GET /reports/data/{report_key}    统一取数入口（16 个 key 全走这里）
GET /reports/export/{report_key}  CSV 导出（四种形态都能导，带 UTF-8 BOM）
```

前端**不写死任何报表清单**：菜单按 `/reports/catalog` 渲染，报表体按
`shape` 选渲染器。以后加一张报表 = 只改后端的 `REPORT_CATALOG` 一个数组。

### 15.4 口径（写进代码注释，免得以后各处算法漂移）

1. **只算真实出库的开单**：`sales_orders.doc_type == "outbound"`。
   `doc_type == "order"` 是「只订货没发货」，不进销售报表 —— 与库存/财务同一口径。
2. **销售退货按负数并入**，得到的是**净销售**。卖 10 件退 3 件，报表显示净 7 件。
3. **毛利 = 净销售额 − 成本**；成本按商品档案的**当前采购价**估算
   （项目没有批次成本核算，这是刻意保留的简化，报表页脚会注明）。
4. **日期取单据自身的业务日期**（`order_date` / `return_date`），取不到才退到 `created_at`。
5. **期间桶有上限（62 列）**：超了直接返回 400 让你缩小范围，
   **绝不悄悄截断** —— 截断出一张少了几列却看不出少的报表，比报错危险得多。

### 15.5 前端：一个目录 + 一个渲染器

`App.jsx` 的「报表中心」从原来的两块静态卡片（销售额/采购额直方图）换成：

- **右**：工具条（起止日期 + 粒度下拉 + 维度下拉 + 筛选 + 导出 CSV）+ 四种形态的渲染分支 + 口径说明；

- 出入库沿用国内习惯：**入库红、出库绿**（与「涨红跌绿」同一套约定）。

### 16.1 路由为什么单独拆一个文件

`app/api/v1/routes/system.py` 是继 `reports.py` 之后第二个从 9000+ 行的 `erp.py` 里拆出来的
模块，理由与报表同源：这里**没有任何单据语义** —— 没有库存流水、没有财务事件、没有
打印与 Excel 注册表，与 `erp.py` 的业务函数零共享。硬塞进去只是让那个文件更难读。

鉴权口径（本模块最重要的约定）：

- 写操作（建 / 改 / 删 / 重置密码 / 启停）一律 `require_roles("admin")`；
- 读操作（部门树 / 角色 / 用户列表 / 权限目录 / 打印模板 / 操作日志）同样要求 admin
  ——「谁能看用户列表」本身就是管理权限的一部分；
- **仅两条例外对任意登录用户开放**：
  `GET /system/me/permissions`（前端菜单过滤的唯一数据源）
  与 `GET /system/lookups`（业务表单的字典候选）。

### 16.2 权限模型：刻意简化到「菜单」

权限最小单位是**菜单 key**（与前端 `menuGroups` 的 `item.key` 一一对应）。
`app/core/permissions.py` 的 `PERMISSION_CATALOG` 是**唯一事实来源**，
内置角色的默认权限与角色管理接口的权限树都从它派生；
`tests/test_system_users.py` 有一条一致性断言用正则从 `App.jsx` 抽 key 集合比对，
两侧一旦漂移就红 —— 加菜单只改前端会被挡住。

- 不做按钮级 / 字段级权限：那需要一整套元数据引擎，收益远小于复杂度。
- `roles.permissions` 存 JSON 文本 `{"all": bool, "menus": [key, ...]}`；
  `all: true` = 超级管理员（admin 角色）永远拥有全部菜单。
- `users.role` 存角色 **code 快照**，JWT 与 `require_roles(...)` 都读它
  —— **鉴权链路零改动**，这是整个权限模型能低成本落地的前提。
- 组织机构是 `departments` 自引用树（`parent_id`，与 BOM 同模式）；
  有子部门或有用户时禁删（409），改父级时用 `_descendant_ids` 阻止成环。

### 16.3 参数设置：只放真会被读取的参数

「改了没反应的假参数」比没有参数页更糟 —— 用户会以为配置生效了。
所以每个内置参数都必须有代码读取点，`test_every_builtin_param_is_read`
逐个去源码里找痕迹，**新增参数忘了写读取代码就红**。

三个内置参数，三个都有真实落点：

| 参数 | 读取点 |
|---|---|
| `print.footer_text` | `erp.py::_pdf_response` → `print_template.resolve_print_spec` → `pdf_render` 页脚段 |
| `system.default_page` | `GET /system/me/permissions` 下发 `ui.default_page`，前端落地页；**不可见时回退**到该用户可见菜单 |
| `stock.warn_enabled` | 库存页预警徽标的显示开关 |

### 16.4 数字字典：给候选，不锁死输入

`data_dictionaries` + `data_dictionary_items`（用 `dict_type` 字符串关联而非外键 id
—— 前端只要一个 type 字符串就能取候选，字典是"配置"不需要被业务单据外键引用）。
前端用 `<datalist>` 挂在付款方式 / 商品单位 / 岗位 / 开户行上：**既给候选又不锁死输入**。

内置 4 组字典（付款方式 7 项、岗位 9 项、计量单位 18 项、开户行 15 项），
字典项停用 / 字典停用会立刻从 `lookups` 候选里消失；内置字典不可删（409）。

### 16.5 打印模板：刻意不做「打印字段表」

浩技云的「字段表管理 / 打印字段表」把标题、抬头、明细列、字段顺序全部做成数据库里的
动态元数据，再交由一个通用表单引擎拼装。**这里拒绝抄这套**：

- 列宽、合计位置、换页阈值这些**只有渲染器才掌握的东西**被搬进了数据库，
  数据库里多一个字段，渲染器就多一个可能猜错的组合；
- 出一张格式错乱的发票 / 送货单，比"模板不能随便改"严重得多。

改用「**模板配置表 + 固定渲染器**」：

- 渲染逻辑（`pdf_render.py`）完全静态，永远只认它显式支持的 key；
- 模板表只放渲染器明确支持、且改完立刻看得见的外观项：
  模板名 / 标题 / 抬头附加文字 / 页脚文字 / 是否打印公司抬头 / 是否打印签章栏；
- `doc_type` **不由用户输入，从打印注册表推导**（`erp.py::printable_doc_types`）。
  新增一张单据的打印就自动多一条模板，不需要在两处维护清单
  —— `test_print_registry_is_covered_by_templates` 会在漏归类时挡住；
- **模板预览接口**用样例数据当场出 PDF：改了有没有效果不必去找一张真单据打一遍
  （样例数据全用一眼假的名字，并标注"不是真实单据"）。

页脚三层优先级：**模板 > 系统参数 `print.footer_text` > 默认页码**，
每层都是"非空才覆盖"，避免管理员只想改页脚时顺手把单据标题清成空白。

### 16.6 操作日志：只记写操作，且不能反过来影响业务

`operation_logs` 表 + `app/main.py` 的 HTTP 中间件。三条不可动摇的约定：

1. **只记写操作**（POST/PUT/PATCH/DELETE）。查询占了请求量绝大多数，
   记进来会把真正要追的"谁改了这张单"淹掉；
2. **写日志绝不允许影响业务**：中间件里所有异常都吞掉（宁可少一条记录，
   也不能让一张已入库的销售单返回 500），落库走 `run_in_threadpool` 不阻塞事件循环；
3. **表会自我修剪**：超过 5000 条按 id 删最老的一批。这是全库唯一一张只增不减的表，
   不修剪几年后会把库撑大。

动作名由 method + url 翻译成人话（"新增客户""重置密码""登录"），
不依赖业务代码手工登记 —— 手工登记这种事一定会有人忘。
末段语义覆盖表处理 `POST /users/7/password` 这类"不是新增"的 POST；
子资源（`/sales-orders/3/items`）补注成"新增销售单（items）"，不掩盖主对象。

**登录失败也留痕**：中间件拿不到请求体，所以由 `auth.py::login_user`
把尝试的用户名放进 `request.state.log_username`（Starlette 的 state 挂在同一个
scope 上，路由与中间件共享）。密码错、账号停用这些尝试都能看出是谁在试。

**清空日志本身也会被记一条**（中间件在响应之后写入）。这是有意为之：
清理行为必须留痕，否则日志可以被无声抹掉就失去了意义。

`target_id` 只对 url 里带 id 的操作（改/删/子资源）有值；新增操作的对象 id 在响应体里，
中间件读不到 —— 读响应流会干扰 PDF 下载这类流式响应，这是刻意的取舍。

### 16.7 踩到的坑：一个被吞掉的 `NameError`

第 2 轮把 PDF 页脚改成读系统参数时，`_pdf_response` 里写了 `SessionLocal()`，
但那个名字**在 `erp.py` 里根本没导入**。偏偏外层 `except Exception: pass`
把它吞得干干净净 —— 参数静默失效、打印照常出纸，只剩"页脚不听配置"这一个怪现象。

修法是两层：**把导入提到模块级**（真出问题立刻暴露，而不是吞进 except），
以及**复用调用方已有的 `db`**，不另开 session。
顺带一个教训：`test_footer_text_reaches_the_pdf` 这条"真改参数 → 真打 PDF → 抠字比对"
的测试，正是为了抓这类**功能照常工作、配置悄悄失效**的故障而写的。

### 17.1 期初建账：不建新表，就是标记过的库存流水

期初库存**没有单独的表**，它是 `inventory_transactions` 里
`related_type = 'opening'` 的流水（`doc_no = 'OPENING'`）。这么定的直接好处：
现存量（`_net_stock_map` 扫全表）、库存报表、成本计算**自动把期初算进去**，
不需要在任何一个地方为"期初"加分支。

代价是这批流水必须和真实业务流水区分干净 —— 所以每一个写操作都死守
`related_type == 'opening'`：

```
GET    /opening-stock               期初一览（每行带 current_stock 与 has_business）
PUT    /opening-stock               批量幂等 upsert（按仓库 × 商品），数量与金额都为 0 视为删除
DELETE /opening-stock/{id}          删单条 —— id 落在同一张流水表里，少一个判断就可能删掉真实出库
POST   /opening-stock/clear         清空全部期初
```

页面把两件容易出事的后果**摆在明面上**：

- 每行显示**现存量**，因为期初直接计入现存量，改期初这个数字就会跟着跳；
- 每行标 `has_business`：该「仓库 × 商品」已经发生过真实出入库时显示「已发生业务」——
  这时候改期初等于凭空挪动历史起点，必须让人看见；
- 删除单条期初的确认框直接写明「现存量会同步减少」；
- 清空期初的确认框写明「期初基数归零」「历史单据不受影响」「只想改几项请用『改这一项』」。

录入走「**草稿清单 → 保存全部**」：先在页面上攒要建的账，一次提交，
与参数页同一套交互习惯。同一「仓库 × 商品」在清单里只保留一行（后填的覆盖先填的），
否则一次提交里会出现两个同样的键，后端 upsert 两次、最后一行赢，人会看糊涂。

另外补了 `GET/PUT /opening-balances`：期初**应收 / 应付**。
`customers.init_receivable` / `suppliers.init_payable` 这两个字段一直都在，
但**客户与供应商档案只支持新增和删除、没有编辑接口**，所以期初往来一直没有入口。
新接口只改 `init_*` 三个字段，不碰档案其它内容 —— 建账归建账，改档案归改档案。

### 17.2 员工档案：和 `users` 是两回事，刻意不合并

`employees` 是**人员名册**（工号/部门/岗位/入职离职/联系方式/在职状态），
和 `users`（登录账号、密码、角色、菜单权限）是两个概念。

进销存系统里最常见的错就是"把两者合成一张表"，后果是逼着给每个员工开登录账号，
权限表和人员表从此缠在一起。车间里绝大多数人根本不会登录 ERP，
但他们需要出现在单据上（业务员、领料人、送货人）。

所以这里**连关联字段都不留**（没有 `user_id`）：需要时再说，
不给未来放一个永远为空的列。另外**只有 `status`（在职/离职），没有 `is_active`** ——
两个布尔表达同一件事必然漂移。

写路径直接复用既有的档案通路：注册进 `_ARCHIVE_KINDS` 就拿到了
409 引用检查 + `force=true` 强制删除 + 批量删除；注册进 `_IMPORT_TARGETS` 与
`excel_io.COLUMNS` 就拿到了模板下载 + 预检 + 导入导出。

### 17.3 Excel 导入的静默丢字段（本轮最隐蔽的坑）

`_import_archive` 是拿到列名**直接 `setattr`** 的。员工档案的「部门」列填的是**名字**、
库里存的是 **id**，直接 setattr 会怎样？

SQLAlchemy 对未映射属性**照单全收**：`obj.department_name = "生产部"`
既不报错也不落库，导入还会返回"成功 1 条"。**字段就这么静默丢了。**

修法是加一层显式翻译（`_translate_import_payload`）：

```python
if kind == "employees":
    if "department_name" in payload:   # 部门名 → department_id，查不到就抛错（变成该行的错误原因）
    if "status" in payload:            # 「在职/离职」→ active/left
```

原则是：**凡是不等于字段名的列，都必须显式翻译**，翻不出来就抛错。
测试 `test_employee_excel_import_resolves_department_and_status` 导入后**回读**，
断言 `department_id` 真的落库了 —— 光看导入返回的成功数抓不住这个问题。

### 17.4 顺手补的关联缺口

- **删除部门时的员工引用检查**：原来只拦「有子部门」「有用户」，
  现在补上「有员工」（409）。不补的话删完部门会留下一批 `department_id`
  指向不存在部门的员工，列表里部门列空白，而且**没有任何入口能修回来**。
- **`GET /system/departments/options`**：任意登录用户可读的部门扁平选项。
  员工档案页要有部门下拉，但它不该为了拿选项而要求管理员权限 ——
  与 `lookups` 同一理由。只返回 id/编码/名称/层级，**不含用户数与负责人**（那是管理信息）。

### 17.5 ⚠️ 一次真实的数据事故与恢复（必须记下来）

**事故**：期初建账的「清空」接口是**全库范围**的，而本项目测试**直连正式库**。
第一版测试顺手调了 `POST /opening-stock/clear` 去验证"只删期初、不动业务流水" ——
这一下把用户真实的 **42 行期初台账（40,609 件 / ¥316,565.32）真的删掉了**。
同一类问题还有一处：`DELETE /system/logs` 在测试里被用来"铺一个干净场景"，
每次跑 pytest 都会抹掉全部操作留痕（与 `clean_test_data.py` 里"不删 admin 日志、
那是真发生过的操作"的既定政策自相矛盾）。

**恢复**：`E://AI//ERP软件//backup//` 里有每日 21:37 的**整库** pg_dump（保留 14 份）。
`erp` 用户没有建库权限，所以没有恢复成临时库，而是：

```
pg_restore --data-only -t inventory_transactions -f x.sql  备份文件
→ 把 COPY 块的目标表名改成临时表，psql 灌进去
→ INSERT INTO inventory_transactions ... SELECT ... WHERE NOT EXISTS(同仓库×商品)
→ 逐行比对：42 行 / 40,609 / 316,565.322，连备注与单号都与备份完全一致
```

**修复**：新增 `tests/prod_snapshot.py`，给"会动到全库数据的测试"一层
**快照落盘 + 断言后还原**的保护：先快照（并写文件，进程被杀也能捞回来）→
调危险接口 → 断言 → 在 `finally` 里还原 → 三项（行数/数量/金额）都对上才删快照文件。
还原失败会**抛出去**，不允许"测试绿了、数据没了"。

**顺带查出的两个真问题**：

1. `GET /opening-stock` 漏了 `note` 字段 —— 页面「备注」列永远是空的，
   而且"载入改这一项"拿不到备注，保存后会被刷成默认的"期初建账"，
   **把用户写的建账说明悄悄改掉**。已补字段 + 补往返测试。
2. `clean_test_data.py` 被我这一轮的补丁改出了一个 `NameError`，
   导致 `run_cleanup` 直接抛错 —— conftest 把异常吞了，所以**清理静默失效**，
   连着两次全量 pytest 的测试残留都留在了库里（累积到 102 个测试商品）。
   已修复，并在预览里补上「测试账号/角色/部门/日志」与 `employees` 的计数
   （原来只剩这几类时预览会误报"没有测试残留"，而 `--apply` 其实会照删）。

教训一句话：**「测试连的是正式库」这个约定，要求测试只能写自己造的数据。
一旦要验证全库范围的接口，必须显式加保护，不能顺手调。**
