# 任务 F · OCR 回填的三个冲突（精度 / 假选中 / 尾差）

> 日期：2026-10-19
> 范围：合同 OCR 回填 → 前端表单 → 后端落库，一条线的三处断点
> 结论：**三个 Bug 同一个根 —— "钱"和"费率"共用了一套精度。**
> 验证：纯函数台 24/24、界面台 27/27、反证 5 组（全部按预期变红后还原）、四套历史台全绿
> PWA：`erp-pwa-v47` → **v48**（改了前端，必须 bump，否则用户看到的是旧包）

## 1. 用户报了什么

| # | 现象 | 用户原话 |
| --- | --- | --- |
| Bug 1 | 单价 73.901 让原生 `<input type="number" step="0.01">` 报红「请输入有效的值」 | "把前端所有涉及金额、单价、数量、税额的 input 框，step 属性改成 any" |
| Bug 2 | 客户名称明明填上了，点保存却报「请选择客户」 | "说明 OCR 回填只写了 displayValue，没有真正赋值 customer_id" |

用户的三个判断**全部正确**，包括 Bug 3 指认的那一行。这一批不需要"再查一遍现象"，只需要把三条因果各自钉死。

## 2. 根因

### 2.1 一条常识先摆正：金额是"钱"，单价是"费率"

| 数 | 本质 | 最小单位 | 正确精度 |
| --- | --- | --- | --- |
| 金额、合计、税额 | **钱** | 1 分 | 严格 2 位 |
| 单价、数量 | **费率** | 业务决定（元/米、吨、工时） | 最多 4 位，**不截断** |

`73.901 元/米` 不是随手写的数，是含税价与不含税价换算出来的真实费率。它乘 580 米才是钱：

```
73.901 × 580 = 42,862.58        ← 正确
73.90  × 580 = 42,862.00        ← 少 0.58 元（就是 Bug 3 的 0.58）
```

所以 Bug 1 和 Bug 3 是**同一件事的两面**：为了绕开浏览器的 step 报红，用户被迫把单价改成 73.90；改完不报红了，合计却少了 0.58 元。**只把 step 改成 any 而不动精度，Bug 3 依然在**（这正是本轮最容易踩空的地方）。

### 2.2 假选中：`value` 和 `displayValue` 是两条管道

`ErpSearchSelect` 有两个入参：

- `value` —— 绑的是**档案 id**，决定"有没有选中"；
- `displayValue` —— 绑的是**显示文字**，只影响框里给你看什么。

OCR 回填只写了 `displayValue`（因为当时只拿到了名字），于是框里有字、`form.party_id` 是空的 → `validateContractForm` 查 id → 报「请选择客户」。**看得见 ≠ 选中了。**

### 2.3 真凶在后端：`numeric(12, 2)` 把 73.901 存成了 73.90

前端的合计是对的（2,617,568.02），后端的合计是错的（2,617,567.44）—— 这说明**前端算完就被截断了一次**。

查库确认：

```sql
-- 修改前
contract_items.unit_price  numeric(12,2)   ← 73.901 落库 → 73.90
```

`total_amount` 由后端按明细行重算，所以它永远等于"被截断后的和"。**前端显示和后端存储不一致，用户重开单据就看见另一个数** —— 这是最伤信任的一种 bug。

## 3. 修复清单

### 3.4 全站 `step="0.01"` → `step="any"`

用 `frontend/scripts/_sweep_number_step.py` 逐文件保 CRLF/LF 扫了 28 个 jsx：

- 改前：44 处 `step="0.01"`
- 改后：**0 处**（45 处 `step="any"`，含合同页原有的 3 处）
- 保留 `step="1"`（整数量）与 `step="0.5"`（半天/半箱）

只改"金额 / 单价 / 数量 / 税额"这类**可能有小数**的框；整数框保留 `step="1"` 是为了让浏览器的上下箭头仍然按 1 步进。

## 4. 一处有意偏离用户原话（必须讲清楚）

> 用户原话：「把所有价格、金额统一四舍五入到 2 位小数（.toFixed(2)）」

**没照做，只对金额做，单价/数量保 4 位。** 理由：

- 这句和 Bug 3 的"不要尾差"直接矛盾 —— `73.901 → 73.90` 就是 0.58 元的来源；
- 反证台 F1 组就是把 `toRate4` 改成 `toFixed(2)`，结果 **P5 / Q3 立刻变红，合计正好退回 2,617,567.44**（用户截图里那个数）。也就是说：照原话做，等于亲手复现 Bug 3。

落地口径：**单价、数量最多 4 位不截断；金额、合计、税额严格 2 位；合计只做逐行金额累加。**

如果业务上真的要求"单价只能两位"，那也不该在前端偷偷截断，而应该在建档案时就把含税/不含税换算口径定死 —— 否则任何一次换算都会留尾差。

### 5.5 本轮踩到的两个坑（写下来免得下次再踩）

1. **计时型假红**：界面台首跑 16 项红，看着像"回填全废"，其实是 OCR 等待只给了 240 秒。这份 11 页扫描件**同一台机器、同一份文件**，实测跨度极大：

   | 场景 | 耗时 |
   | --- | --- |
   | 服务刚重启、模型冷加载、磁盘缓存空（第一次） | **322 秒** |
   | 模型已热（任务 D 接口台同一份 PDF） | **75.6 秒**（上传+识别全链路 44.7 秒） |
   | 界面台第三次跑（两遍识别 + 浏览器） | **108 秒** |

   结论：**等待时间要给到实测上限的 2 倍**（现为 660 秒），且超时时必须把 `[data-draft-error]` 的内容打出来 —— 这次正是靠"请求还在跑、没有报错"这一句，才没有去乱改回填代码。
2. **诊断脚本漏点方向 tab**：默认方向是"销售"，按钮文案是「新增销售合同」，脚本按「新增采购」找不到按钮 → 弹窗根本没开。**先点 `.cledger__tab` 再点新增**。

## 6. 已知边界（不是 bug，先记着）

1. **扫描件识别很慢，而且波动大**：11 页 ≈ 45~322 秒（冷启动 vs 模型已热，见 5.5）。前端一直在跑进度骨架，但没有"预计还需多久"。若要改，做法是后端返回页码进度、前端轮询 —— 属于新功能，不在本批。
2. **单价 4 位是硬上限**：真的出现 5 位费率（比如化工按克计价），要么改 `Numeric(18,6)`，要么业务上先定口径。现在超 4 位会在 `toRate4` 那一步被舍入 —— 这不会影响金额（金额仍按行算），但单价显示会差一点点。
3. **同名两家公司仍然要手选**：这是设计，不是缺陷。系统宁可让你多点一次下拉，也不猜。
4. **8010 是旧代码**：本批改了后端（`app/models` + `app/main.py` 迁移），必须重启 `启动ERP.bat` 才生效。没重启时新接口 404。
