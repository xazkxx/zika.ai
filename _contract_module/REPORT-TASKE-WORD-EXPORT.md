## 一、为什么做这件事

在这之前，用户想把单据发给客户/供应商只有两条路：

1. **打印成 PDF**（`/print/xxx`，HTML→PDF），拿不到可编辑文件，对方要改一个错别字只能整单重开；
2. **截图贴进 Word 自己重排**，几十行明细根本排不齐。

Word 是商务往来里唯一"能盖章、又能改"的载体。所以这一批的目标不是"再出一个导出格式"，而是
**让系统直接产出可以直接盖章的正式文件**：抬头、编号、双方信息、明细表、金额大写+小写、签字栏，一样不能少。

### 2.3 顺手修掉的用户反馈：明细 0 行

用户在任务 D 验收后立刻反馈：*"识别的明细行是 0 行。这份合同金额高达 261 万，明细肯定不止一条。"*

**根因不是"漏读"，也不是"JSON 到表单漏映射"** —— 是**第三种表格形态**：
这份合同的「附件一 分项报价表」被 rapidocr 按**单元格**切开，输出成

```
序号 → 名称 → 单位 → 数量 → 单价 → 金额   （各占一行，纵向排列）
```

而引擎原来只认两种形态：① 文本层一行四列；② 连续 4 行 名称/数量/单价/金额。
形态③ 一行都匹配不上 → `items` 为空数组 → 前端明细 0 行，但头部字段全对（所以看起来"识别很成功"）。

**修法**：新增 `_match_seq_item()`（`contract_ocr.py`），认"序号打头、每格一行"，且
**唯一敢认的依据是 `数量 × 单价 ≈ 金额`**（容差 `max(1.0, money × 0.005)`）。
这条校验让"认错"几乎不可能——数字对不上的组合直接丢掉，宁可漏不可错。

修复后同一份真实合同认出 **5 条**，合计 `2,617,568.02`，与合同总额**分厘不差**：

| 品名 | 单位 | 数量 | 单价 | 金额 |
| --- | --- | --- | --- | --- |
| ZRC-YJY23-0.6/1kV-3x25 | 米 | 4654 | 100.81 | 469,169.74 |
| ZRC-YJY23-0.6/1kV-4x35+1x16 | 米 | 3119 | 233.00 | 726,727.00 |
| ZRC-YJY23-0.6/1kV-4x70+1x35 | 米 | 2766 | 463.10 | 1,280,934.60 |
| ZRC-YJY23-0.6/1kV-4x50+1x25 | 米 | 306 | 319.85 | 97,874.10 |
| ZRC-YJY23-0.6/1kV-3x16 | 米 | 580 | 73.901 | 42,862.58 |

前端同步三处：
- 明细表**新增「单位」列**（原来只有名称/数量/单价/金额，单位白丢）；
- `ocrItemsToRows` / `applyDraftOcr` 的单位回填改成 `productHit?.unit || String(item.unit || '')`；

## 三、排版做到了什么（这是本批的重头）

用户的要求是"排版必须完美"。逐项落实：

| 要素 | 实现方式 | 为什么必须这样 |
| --- | --- | --- |
| **公司抬头** | 公司名 16pt 黑体居中 + 地址/电话/税号 8pt 一行 + 一条下边框横线 | 抬头没设时给「（公司抬头未设置，请到「系统设置 → 公司信息」补全）」——**留白比提示更糟**，打印出来就是一张没抬头的纸 |
| **单据编号 / 日期** | 一行元信息，用「　　」全角空格隔开 | 编号、日期、地点一行看完，不用上下找 |
| **双方信息块** | 2 列无框表，左我方/右对方（或左客户/右报价单位） | 名称、税号、法人、地址、联系人、电话、开户行、账号八项，合同要素齐全 |
| **明细表格** | `Table Grid` 框线 + 灰底表头（`F2F2F2`，黑白打印也分得清） | — |
| **表头跨页重复** | `w:tblHeader` | 明细超过一页时第 2 页仍有列名，不用翻回去对列 |
| **列宽** | **逐格** `cell.width = Cm(...)`，`autofit=False` | ⚠️ 只设 `column.width` 在 Word 里**完全不生效**（老坑，反证 P6 钉住） |
| **金额大写 + 小写** | 合计行左格「合计（人民币大写）：贰佰陆拾壹万…」，右格「¥2,617,568.02」 | 合同只写小写不合规 |
| **中文字体** | `_cn_font()` 逐 run 设 `w:ascii` / `w:hAnsi` / **`w:eastAsia`** | ⚠️ 只设 `run.font.name` 只写 ascii/hAnsi，**中文在 Word 里掉回"等线"**（反证 P1 钉住） |
| **签字栏** | 3×2 表：盖章 / 代表 / 日期 | 采购合同左右自动对调（我方=需方，对方=供方），不让对方签错边 |
| **页脚** | 公司名 + `第 {PAGE} 页 / 共 {NUMPAGES} 页`（域，不是写死） | 插页删页自动更新 |
| **零明细** | 明细表写「（无明细）」占位 | 空表看起来像文件坏了 |
| **条款区** | 只印有值的项，一条一行 | 没填的条款不留一堆空标题占地方 |
| **违约金** | `penalty_rate=0.0005` 印成「每日 0.05%（约万分之5）」 | 别把 0.0005 直接印给客户看 |

页面：A4 210×297mm，页边距 左右 2.2cm / 上下 1.8cm。

## 四、接口设计上的两个刻意取舍

1. **默认返回二进制，不用 base64。**
   `application/vnd.openxmlformats-officedocument.wordprocessingml.document` **不会被浏览器阅读器接管**
   —— 那是 PDF 的毛病（PDF 的 fetch 响应会被浏览器抢走，204+空 body 但 `ok` 仍为 true，静默 0 字节）。
   docx 直取更省一次编解码。但仍留了 `?as_json=true` 旁路（返回 base64），
   给"公司电脑装了下载拦截插件"的场景排查用。

2. **导出是纯只读操作。**
   不写库、不改状态、不产生流水、不动库存。所以不做权限细分，但**必须带 token**
   —— `get_db` 按 token 定 schema，跨账套导出的数据就是事故。

文件名净化：`_safe_filename()` 把 `/ : * ? " < > |` 换成下划线（中文保留），
再用 RFC 5987 传给浏览器（`filename*=UTF-8''…`），前端从 `Content-Disposition` 取真名。
回退到 ASCII 兜底名时中文会变下划线 —— 所以前端必须优先读 `filename*=`。

### 5.3 明细行修复的反证（`_contract_module/_probe_items.py`）：**3 组全红 → 全绿**

形态③ 的主验证台要真跑 OCR（11 页扫描件 ≈ 9 分钟），拿它做反证太贵。
所以另开一个台，用**缓存好的真实 OCR 行**（`_items_lines.json`，348 行）直接打 `parse_fields()`，一次 0.5 秒：

| ID | 改坏什么 | 样本 | 结果 |
| --- | --- | --- | --- |
| I1 | 去掉 `数量×单价≈金额` 校验 | 陷阱：`1/假冒品名A/米/10/100/5000`（10×100≠5000） | ✅ 基线 0 条 → 改后误认 1 条 |
| I2 | 整个不调 `_match_seq_item()` | 真实合同 348 行 | ✅ 基线 5 条 / ¥2,617,568.02 → 改后 0 条 |
| I3 | 序号规则放宽成任意数字串 | 陷阱：`4654/品名B/米/4654/100.81/469169.74` | ✅ 基线 0 条 → 改后把数量当序号，误认 1 条 |

**这里踩到一个坑值得记**：第一版三组 break 全都"没变红"，原因是只 `del sys.modules['app.services.contract_ocr']`
**不够** —— `app.services` 这个包里还挂着同名属性，`from app.services import contract_ocr` 会直接拿到旧对象，
于是"改的是磁盘、跑的是内存"。必须连 `delattr(app.services, 'contract_ocr')` 一起做。

**I1/I3 为什么要专门造样本**：真实合同恰好没踩这两个坑，直接拿它反证，这两处 break 不会变红 ——
那时变红的是"样本没覆盖"，不是"代码对"。反证的价值在于**让错误暴露**，样本必须能出错才行。

## 八、已知边界（写清楚，不藏）

1. **只覆盖四种单据**。销售订单/销售出库/采购退货/销售退货等暂时没有 Word 导出按钮
   —— 后端 `_render` 加一个分支 + 前端加一个 `data-word-export` 就能扩，不是重构。
2. **明细最多 20 条**（OCR 侧 `items[:20]` 截断）。导出侧不截断，这条只影响 OCR 回填。
3. **对账单的明细顺序**按 `line_no` 再按 `id`，与界面一致；`line_no` 为空时按 `id`。
4. **导出的 Word 与系统数据不再关联** —— 用户在 Word 里改了，系统里不会变。使用说明里写明了。
5. **没有做"多语言/多币种"** —— `currency` 目前只印 CNY，外币单据会印成"¥"。
6. **合并单元格**在 python-docx 里读回时文本会重复（合计行合并 6 格读回 6 次），
   Word 里渲染是正常的一格 —— 只影响脚本读回，不影响用户看到的文件。
