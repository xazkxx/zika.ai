# 第一部分：发票问题诊断（有铁证）

## 1.1 样本

`data/invoices/` 里 12 份真实发票，均为**国家税务总局全电发票（数电票）**导出 PDF，
文件名形如 `dzfp_26612000001003603936_陕西送变电工程有限公司_20260527163115.pdf`。

## 1.2 PDF 的三层结构（这是关键）

以 `dzfp_26612000001003603936...pdf` 为例：

**① 二维码（300×300 图片对象，xref=14）** —— 解码结果：

```
01,31,,26612000001003603936,4862.50,20260527,,5F18
 │  │   │  └── 发票号码        └ 价税合计  └ 开票日期  └ 校验位
 │  └ 票种代码
 └ 固定标识
```

这就是**数电票的标准二维码格式**。三个字段（**发票号码 / 价税合计 / 开票日期**）
由税局生成，**100% 准确，不存在识别错误**。

⚠️ 二维码里**没有**买卖方名称/税号，也**没有**明细行 —— 这三类只能走文本层。

**② 文本层：标签与值是分离的两个块**（这是现有识别出错的直接原因）

```
[标签块]  电子发票（增值税专用发票）/ 发票号码： / 开票日期： / 购买方信息 /
          统一社会信用代码…： / 销售方信息 / 名称： / 项目名称 / 单价 / 金额 …
[值块]    26612000001003603936 / 2026年05月27日 / 陕西送变电工程有限公司 /
          916101332206045948 / 陕西寨纬智能科技有限公司 / 91611104MA6TJURR23 /
          ¥4814.35 / ¥48.15 / ¥4862.50 / *塑料制品*PVC管材 / 1% / 米 / 1138.61 …
```

现有 `_extract_invoice_summary()` 用的是 **「标签后紧跟值」** 的正则
（如 `名称[:：]\s*([^\n]{2,40})`）。标签块里的 `名称：` 后面**根本没有值**，
所以这些正则**永远匹配不到**，只能靠兜底猜测填值 —— 这就是"识别错误比较多"。

**③ 版式是表单**，所以标签与值可以**按坐标就近匹配**：

| 标签 | 坐标 | 值 | 坐标 |
|---|---|---|---|
| `发票号码：` | x=438 y=32 | `26612000001003603936` | x=482 y=32 |
| `开票日期：` | x=438 y=49 | `2026年05月27日` | x=482 y=49 |
| **`购/买/方/信/息`（竖排）** | **x=17** | `名称：` x=33 → `陕西送变电工程有限公司` | x=57 y=96 |
| | | `统一社会信用代码…：` x=33 → `916101332206045948` | x=153 y=123 |
| **`销/售/方/信/息`（竖排）** | **x=302** | `名称：` x=318 → `陕西寨纬智能科技有限公司` | x=340 y=96 |
| | | `统一社会信用代码…：` x=317 → `91611104MA6TJURR23` | x=438 y=123 |

## 1.3 🚨 已确认的实质性错误：买卖方搞反了

**坐标铁证**：`购/买/方/信/息` 五个字在 **x=17**（左栏），`销/售/方/信/息` 在 **x=302**（右栏）。

因此这张发票的正确值是：

| 字段 | **正确值** | 库里现存 |
|---|---|---|
| 购买方名称 | 陕西送变电工程有限公司 | 被当作 `seller_name` ❌ |
| 购买方税号 | 916101332206045948 | |
| 销售方名称 | 陕西寨纬智能科技有限公司 | 被当作 `buyer_name` ❌ |
| 销售方税号 | 91611104MA6TJURR23 | |

**真实影响**：
- **进销项判断会整体反向** —— 因为我方（抬头）若是"陕西送变电工程有限公司"，
  本该判为**进项**（对方开给我们），却因为买卖方反了而判成销项。这类错误**看不出来**。
- 这是系统性的：12 张发票大概率全反（同一套导出模板）。

> 顺带说明：早期那 2 张发票（`25612000000093948510` / `26612000001006203301`）
> 来自不同模板（文本层里标签与值是连在一起的），所以它们的买卖方**可能是对的**。
> **不能用同一套逻辑硬套两种模板** —— 见 2.3。

## 1.4 现有流水线的三处缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 二维码这一关**没有覆盖数电票的逗号分隔格式**（`01,31,,号码,金额,日期,,校验`） | 走了兜底的文本层，白白丢掉了最准的三个字段 |
| 2 | 文本层提取只认"标签后紧跟值" | 数电票匹配不到 → 靠猜 → 买卖方反了 |
| 3 | 明细行没有解析（只存了"发票扫描结果"一条占位） | 用户要的"明细单价/数量/合计"根本没有 |

# 第二部分：发票识别与页面改造方案

## 2.1 识别：三层流水线重排（**二维码绝对优先**）

```
第 1 关  二维码（cv2.QRCodeDetector，已装 opencv-contrib-python 4.11）
         ├─ 支持数电票逗号格式：01,31,,号码,金额,日期,,校验
         ├─ 支持 JSON / XML / 旧增值税发票的 01,10,代码,号码,金额,日期,校验码
         └─ 拿到：发票号码 ✅ 价税合计 ✅ 开票日期 ✅   ← 命中即锁定，后续不再覆盖
第 2 关  PDF 文本层 + **坐标就近匹配**
         ├─ 按 x 分栏：x < 页宽/2 → 左栏（购买方）；x > 页宽/2 → 右栏（销售方）
         ├─ 用竖排单字（购/买/方/信/息）**动态定位栏位**，不写死 x 值
         └─ 拿到：购买方名称+税号、销售方名称+税号、明细行、合计/税额
第 3 关  OCR（仅前两关都失败时）
```

**坐标匹配的具体做法**（不写死坐标，按相对位置算）：

1. 先找竖排标签：把页面单字按 x 聚类，识别出 `购→买→方→信→息` 与 `销→售→方→信→息` 两组，
   取各自 x 作为**左右栏锚点**（不同 PDF 生成器页宽不同，写死 17/302 迟早失效）。
2. 在每栏锚点右侧、同一 y 行附近找 `名称：` / `统一社会信用代码…：`，
   取该标签**右侧最近的、x 更大的文本**作为值。
3. 若找不到竖排标签（老版式），退回"标签后紧跟值"的老逻辑 —— **两条路都留着**，
   按"哪条能填满必需字段"择优。

**明细行解析**：明细区按 y 分组，每行取
`项目名称 / 规格型号 / 单位 / 数量 / 单价 / 金额 / 税率 / 税额` 八个字段（缺失留空，不猜）。
**关键**：数量×单价 ≈ 金额 这一条做**自校验**，对不上的行标出来让用户看着办，而不是静默存错值。

## 2.2 二维码可下载

- **来源**：直接从 PDF 提取原图（`page.get_images()` → `Pixmap` → PNG），
  这是**原始二维码**，不重新生成、不失真。
- **导出**：提供"下载二维码"（单张 PNG）与"二维码汇总导出"（批量打包
  `号码.png` + 一份 `清单.csv`，含号码/金额/日期/校验位）。
- 若某张发票没有二维码（老式纸质扫描件），按钮置灰并提示"这张发票没有二维码"。

# 第三部分：借 ERPNext 账务模型（补最缺的那层）

## 3.1 为什么是这个

现有后端 14,146 行里**没有科目表、没有凭证、没有试算平衡**。
财务只有两张流水表（`financial_transactions` 按 `transaction_type` 分 24 种事件）。
ERPNext 二十年沉淀最厚的恰好是这块：`GL Entry` 复式记账。

**目标**：不动任何现有单据，加一层总账，把"流水台账"升级成"能对外交代的账"。

## 3.2 四张表 + 一个钩子

| 新表 | 字段要点 |
|---|---|
| `accounts` 科目表 | `code`（如 1001）、`name`、`root_type`（资产/负债/权益/收入/费用）、`parent_id`（树）、`is_group`、`is_active` |
| `journal_entries` 凭证 | `entry_no`（记-YYYYMM-0001）、`entry_date`、`period`、`memo`、`source_type`、`source_id`、`status`(draft/posted) |
| `journal_entry_lines` 分录 | `entry_id`、`account_id`、`debit`、`credit`、`party_type`(客户/供应商)、`party_id`、`remark` |
| `posting_rules` 过账规则 | `doc_type`（复用已有 24 种 `DOC_TYPES`）、`debit_account`、`credit_account`、`amount_field`、`enabled` |

**唯一挂钩点**：现有"单据审核后自动写流水"的那个函数里，多调一次
`post_journal(entry)` —— 与 `_revert_finance`（删单冲销）配对，删单时反向冲红。

**科目表种子**（按小企业会计准则精简，约 40 个科目）：
1001 库存现金 / 1002 银行存款 / 1122 应收账款 / 1123 预付账款 / 1405 库存商品 /
1601 固定资产 / 2202 应付账款 / 2203 预收账款 / 2211 应付职工薪酬 / 2221 应交税费 /
4001 实收资本 / 4103 本年利润 / 6001 主营业务收入 / 6401 主营业务成本 / 6601 销售费用…

**过账示例**（销售开单）：
```
借 1122 应收账款    ¥X
  贷 6001 主营业务收入  ¥X/1.13
  贷 2221 应交税费-销项  ¥X/1.13*0.13
借 6401 主营业务成本  ¥Y
  贷 1405 库存商品      ¥Y
```

**三张报表**：科目余额表 / 明细账 / 试算平衡（借贷是否相等，这是"账做对了"的唯一证明）。

## 3.3 与"余额口径"的关系（重要，别冲突）

第 8 批定过：**资金账户余额 = 期初 + 真实资金移动**（收付实现制），应收应付不进余额。
**总账是另一回事**：它按**权责发生制**记账，应收应付要进。
所以两者**并存不矛盾**：资金账户余额回答"手上还有多少钱"，总账回答"这段期间赚了多少"。
方案里要写清这个区别，否则以后一定有人想去"统一"它 —— 那就两个都不准了。
