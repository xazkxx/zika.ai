# 多公司（多账套）方案评估

> 需求原文：「好几个公司的话怎么办，都是独立账户，仓库和库存可以互调，开票税点参考国家税务可选」
>
> 本文只做**评估与方案对比**，不含实施。第 3 项（开票税点）已单独完成，见文末。

---

## 一、先把现状说清楚（实测，不是推测）

| 事实 | 位置 | 对多公司意味着什么 |
|---|---|---|
| **全库 52 张表，没有任何 `company_id` 之类的租户字段** | 全库 | 现在是彻底的**单账套** |
| 公司抬头是 `company.json`（8 个字段） | 项目根目录 / exe 同目录 | 这是**部署级**配置，一台机器一份。多公司必须把它降为**账套级** |
| 进销项判定读 `company.json` 的税号 | `detect_direction()` + `/invoices/redetect` | 换个公司抬头，重判结果就变 —— 多公司下**每家公司必须有自己的抬头** |
| 用户表无公司归属，JWT 只带 `role` | `models/user.py` / `core/security.py` | "独立账户"如果指独立登录，也要加公司维度 |
| 唯一约束遍布全库 | `products.sku`、`customers.code`、`warehouses.code`、`invoices.invoice_no`、各种 `*_no` … | 这是**方案 B 的暗礁**，见下文 |
| 库存流水靠 `related_type + related_order_id` 溯源，删单可反冲 | `models/inventory.py` | 互调要沿用这套溯源与反冲机制 |
| 同公司调拨**不写财务流水** | `models/inventory_transfer.py` | ⚠️ 公司**之间**的调拨在税法上是**销售**，必须写财务流水 + 开票。这两件事必须先分开 |
| 测试全部直连正式库、大量断言"全库合计" | `tests/` 共 395 条 | 加租户维度后回归成本极高（方案 B 的主要代价） |

当前数据规模：商品 262 / 客户 25 / 供应商 61 / 仓库 7 / 发票 12 / 库存流水 45。
数据量不大，**现在是切多账套成本最低的时机**。

## 二、三个诉求的实质

| 诉求 | 实质 | 难度 |
|---|---|---|
| 好几个公司，都是独立账户 | **多账套**：账不混、报表不串、各报各的税 | 大（架构级） |
| 仓库和库存可以互调 | **公司间调拨** —— 税务上是**内部购销**，不是普通调拨 | 中（依赖多账套） |
| 开票税点参考国家税务可选 | **税率字典** | 小（✅ 已完成） |

## 三、三种做法对比

### 方案 A：多账套 · 一公司一个数据库（推荐）

后端按登录用户所属公司，把 `Session` 路由到对应的库。

| 维度 | 评价 |
|---|---|
| 隔离强度 | ★★★★★ 物理隔离，账**不可能**串 |
| 改动面 | **中**。核心只在 `get_db()` 的 engine 选择 —— 业务代码只认 `Session`，一行不用动 |
| 唯一约束 | **不用改**（每库独立，`sku` 各自唯一） |
| 串账风险 | 无。跨库要显式连过去，不会"忘了过滤" |
| 跨公司调拨 | 一处跨库逻辑（要写补偿/幂等） |
| 合并报表 | 需要聚合多库（应用层聚合或 postgres_fdw） |
| 备份/交付 | 按公司独立备份，单家公司可单独交付 |
| 迁移 | 现有库整体注册为「账套 1」，业务数据零改动 |

### 方案 B：单库多租户（每张表加 `company_id`）

| 维度 | 评价 |
|---|---|
| 隔离强度 | ★★★ 逻辑隔离，**完全靠代码正确** |
| 改动面 | **极大**：52 张表 + 每一条查询都要带 `company_id` 过滤 |
| 唯一约束 | ⚠️ **全部要改成复合唯一** `(company_id, xxx)`。全库十几处 |
| 串账风险 | ⚠️⚠️ **高**。漏一个 `WHERE company_id=...` 不是报错，是**静默串账** —— 这类 bug 在报表上表现为"数字不对"，很难定位 |
| 跨公司调拨 | 最自然（同库、同事务、真 ACID） |
| 合并报表 | 同库直接 join，最简单 |
| 测试回归 | 395 条测试大量依赖"全库合计"，几乎每条都要加租户过滤 |

**结论：B 只在"跨公司业务极其频繁、且需要强一致事务"时才值得。** 本项目当前的痛点是"账要分开"，
不是"跨公司要强一致"，用 B 是拿**全项目的串账风险**去换一处跨库事务的便利。

### 方案 C：多实例（每公司一套部署 + 独立库）

| 维度 | 评价 |
|---|---|
| 隔离强度 | ★★★★★ 进程级 |
| 改动面 | **几乎为零** —— 现在就能做，复制一份部署换个端口与库即可 |
| 跨公司调拨 | ✗ 要跨系统对接，系统帮不上忙 |
| 运维 | N 套要升级、N 个地址、N 份备份 |
| 合并报表 | 要外部汇总 |

**结论：如果两家公司只是"各自独立用"，不需要系统自动联动互调，C 是最省事的。**

## 四、推荐：A（多库账套）

### 为什么不是 B

三处硬伤，任何一处都足以否掉它：

1. **唯一约束**。`products.sku`、`customers.code`、`suppliers.code`、`warehouses.code`、
   `invoices.invoice_no`、各单据的 `*_no` —— 全库十几处 unique 索引都要改成
   `(company_id, xxx)` 复合唯一。改完之后，Excel 导入的"按编码匹配已有档案"、
   各处 `get_or_create`、去重逻辑**全都要跟着改**。
2. **静默串账**。漏掉一处过滤不会报错，只会让 A 公司看到 B 公司的数。
   这种 bug 在业务上表现为"金额不对"，排查成本极高 ——
   而 ERP 的**唯一底线就是账不能错**。
3. **回归成本**。现阶段 395 条测试直连正式库、大量断言全库合计。
   引入租户维度后这些断言要么全部重写、要么全部失效，
   投入远超实现本身，而收益只是"跨库事务方便一点"。

### 为什么不是 C

C 唯一的硬伤是**互调**。而用户明确提了"仓库和库存可以互调"。
但如果用户接受"人工对账"（A 公司开一张销售单、B 公司自己开一张采购单），C 立刻变成最优解。

→ **这是需要拍板的第一个问题，见第六节。**

## 五、实施分期（选 A 的话）

### 第 1 期：账套底座（必做，且要单独上）

1. **`companies` 表**（放一个小的元数据库，或暂放主库）
   ```
   id / code(账套号) / name(公司名) / tax_no(本公司税号)
   db_name / db_url(可空，留自定义) / is_active
   legal_person / address / phone / bank_name / bank_account   ← 就是现在 company.json 那 8 个字段
   ```
   **公司抬头从"部署级"降为"账套级"是本期的关键动作。**
2. **`users.company_id`**（或 `user_companies` 关联表，支持一个用户管多家）
3. **登录流程**：返回该用户可进入的账套列表 → 选账套 → JWT 带 `company_id`
4. **`app/db/session.py` 加账套路由**
   ```python
   _engines: dict[str, Engine] = {}      # 必须缓存：每次 create_engine 会新建连接池
   def engine_for(company_code: str) -> Engine: ...
   def get_db(request) -> Session: ...   # 按 JWT 里的 company_id 取库
   ```
   ⚠️ 这是 A 方案**唯一**需要改的基础设施。所有业务路由、模型、测试都不用动。
5. **`scripts/create_company.py`**：建库 → 建表 → 播种（管理员 / 角色 / 菜单 / 字典 / 参数 / 打印模板）
6. **`company.json` 退化为兼容层**：读抬头时先查账套表，没有再回落 json —— 保证老部署不炸
7. **前端**：登录页加账套选择；顶栏显示当前公司名；「系统设置 → 公司信息」改为写当前账套
8. **升级脚本** `scripts/upgrade_to_multicompany.py`：
   把现有库注册为「账套 1」，并把 `company.json` 里的抬头搬进账套表。**业务数据零改动。**

> 第 1 期做完，用户就能"一家公司一个账套、各登各的、账互不可见"。这已经满足需求的前半句。

### 第 2 期：公司间调拨（必须等第 1 期稳定）

9. **新表** `inter_company_transfers` / `_items`（放在发起方所属库）
   ```
   transfer_no / from_company_id / to_company_id / transfer_date
   settle_mode(成本价 | 售价 | 协议价) / status
   linked_sales_order_no / linked_purchase_order_no
   ```
10. **业务语义（最要紧的一点）**

    ```
    发起 A → B 调拨
      → A 出库（A 库流水 outbound）
      → B 入库（B 库流水 inbound）
      → A 生成销售出库单（销项）    ← 必须
      → B 生成采购入库单（进项）    ← 必须
      → 双方各自开票
    ```

    ⚠️ **公司之间的货物流转在税法上是"销售"**，必须确认收入、结转成本、开具发票。
    绝不能沿用同公司调拨那套"不写财务流水"的做法 —— 那不是简化，是**漏税**。
    `models/inventory_transfer.py` 的注释已经写明同公司调拨为什么不写财务流水，
    公司间调拨必须走相反的规则，两者在代码里要显式区分（不同表、不同状态机）。

11. **跨库一致性 —— 这是 A 方案的代价所在**
    - 两个库不在一个事务里，**必须**做幂等 + 补偿
    - 状态机：`draft → out_done → in_done → completed`
    - 每步按 `transfer_no` 查重（重复提交不能重复出货）
    - `in_done` 之前允许反冲；之后只能红冲
12. **价格**：默认按调出方**成本价**结转（内部调拨的常见做法），也允许按售价（视为正常购销）

## 六、需要拍板的三个问题

| # | 问题 | 为什么它决定方案 |
|---|---|---|
| 1 | **互调要不要系统自动联动？** 还是"各开各的单、人工对账"就行？ | 要自动 → 选 A（C 做不到）；只需人工 → **C 最省事，零代码改动** |
| 2 | **"独立账户"指的是独立账簿，还是独立登录账号？** | 独立账套已含独立账号；若只需账号隔离，可能连第 1 期都不用做 |
| 3 | **几家公司之间要不要合并报表？**（老板想知道"集团总共赚了多少"） | 要合并 → A 需额外做聚合层；只看单家 → 忽略此项 |

**我的建议**：先做**第 1 期（账套底座）**。
它无论后续选什么都不会白做 —— 即使最后选 C，账套表也能作为"部署登记表"用。
而第 2 期（互调）必须等第 1 期稳定后再上，因为它是唯一需要跨库事务的功能，风险集中在那里。

## 七、附：开票税点（已完成 ✅）

### 依据

《中华人民共和国增值税法》**2026-01-01 施行**，第十条（税率）、第十一条（征收率），
辅以各地税务局答疑口径：

| 税率/征收率 | 适用范围 |
|---|---|
| **13%** | 销售货物、加工修理修配、有形动产租赁、进口货物 |
| **9%** | 交通运输 / 邮政 / 基础电信 / 建筑 / 不动产租赁、销售不动产、转让土地使用权；农产品、食用植物油、食用盐、自来水、暖气、燃气、图书报刊、饲料化肥农药农机农膜 |
| **6%** | 销售服务、无形资产（上述两档之外的） |
| **3%** | 简易计税**法定**征收率（小规模纳税人及一般纳税人简易计税） |
| **1%** | 小规模纳税人 3% 征收率减按 1% 征收的**阶段性优惠** |
| **0%** | 出口货物；跨境销售国务院规定范围内的服务、无形资产 |

### ⚠️ 两个必须写进代码的注意点

1. **没有 5%。** 增值税法把简易计税征收率统一为 3%，**取消了营改增时期
   不动产租赁/销售等适用的 5% 特殊征收率**。旧资料和很多老 ERP 的默认字典里 5% 还在，
   保留它会让用户照着开错票 —— 已写测试明确挡住。
2. **字典只是候选，不是税收判据。** 具体业务适用哪一档由交易性质决定，
   最终以主管税务机关口径为准。所以做成**可维护的字典**，不硬编码成枚举；
   界面上也允许自由填写。这一点在字典描述里对用户可见。

### 已落地的改动

| 位置 | 改动 |
|---|---|
| `models/system_config.py` | 内置字典 `tax_rate`，6 项，带适用范围说明 |
| `main.py` | 字典播种支持 `{value, label}` 形式（原来只支持纯字符串） |
| `models/product.py` + `schemas.py` | 商品档案加**默认税率** `tax_rate`（可空） |
| `main.py` | `PRODUCT_ADDITIONS` 加列迁移 |
| 前端 | 数字字典新增「开票税率 / 征收率」可维护；商品档案可设默认税率；发票编辑弹窗税率带候选下拉 |
| 测试 | `test_tax_rate_dictionary_matches_the_vat_law` 等 4 条 |

**为什么商品税率留空而不是默认 13%**：不同商品适用不同档（货物 13 / 农产品 9 / 服务 6），
预设一个"看起来合理"的值，用户不改就会开错票。留空逼着人选。
同理，**不传税率时存 `NULL` 而不是 `0`** —— `0%` 是出口货物的税率，含义完全不同。
