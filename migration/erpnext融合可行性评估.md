**结论：数据不是障碍。真正的障碍在下面第二节和第三节。**

## 二、特色设计框架（"6 个插座"）

进销存系统的难点从来不是页面，而是**一张单据要同时牵动库存、财务、打印、导出、权限五条线**。
我们把这五条线都做成了**注册表**：

| 插座 | 位置 | 现状 | 新模块怎么挂 |
|---|---|---|---|
| ① 财务事件字典 `DOC_TYPES` | `models/finance.py` | **24 种**业务事件类型 | 待建模块的类型基本都已登记 |
| ② 库存流水溯源 | `inventory_transactions.related_type/related_order_id/doc_no` | 采购入/销售出已跑通 | 写一条带 `related_type` 的流水即可自动进库存 + 支持删单冲销 |
| ③ 财务流水多维 | `financial_transactions` + `direction/period/product/warehouse/project` | 期间(YYYY-MM)已建索引 | 单据审核后自动写流水 |
| ④ 打印注册表 | `erp.py::_PRINT_KINDS` | **20 种单据模板**，模板表自动播种 | 一行登记即获得模板 + 预览 + 下载 |
| ⑤ Excel 导入导出注册表 | `services/excel_io.py` 的 COLUMNS/TITLES/KEY_FIELDS | 5 类档案 | 加一组列定义即得模板 + 预检 + 导入导出 |
| ⑥ 菜单框架 | `menus` 表 + `menuGroups` 种子 | **51 菜单全部实装**，动态菜单支持三级 | 摘 todo + 加一个渲染分支 |

### 另外四项工程特色

1. **权限模型与菜单解耦**：权限点 = **页面**（固定清单）；菜单树只管展示。角色权限不会因为管理员调整菜单而漂移。
2. **余额口径采用收付实现制**：资金账户余额只认**真实资金移动**（日常收支/收付款/转账），应收应付、成本结转、报损报溢**不进余额**。
3. **浏览器二进制的正确姿势**：PDF/原件一律走 base64 JSON 通道 —— 因为 `application/pdf` 会被浏览器内置阅读器接管、`fetch()` 拿空响应后静默存 0 字节文件。
4. **幂等播种 + 只补不覆盖**：角色/字典/参数/打印模板/菜单全部"只在表为空时播种"，管理员改过的东西不会被重启冲掉。

## 三、ERPNext 侧的关键事实

| 维度 | ERPNext |
|---|---|
| 底座 | **Frappe Framework**（元数据驱动，DocType = 表 + 表单 + 权限 + 工作流） |
| 语言/栈 | Python + Node + **Redis** + wkhtmltopdf + nginx |
| 数据库 | **MariaDB 10.6+ 为第一公民**；PostgreSQL 非官方一等支持（社区反馈"要改核心"，v16 beta 才列入支持列表） |
| 部署 | **Linux / macOS**（`bench` 只支持这两个平台，Windows 需 WSL2 或 Docker）；标准 Docker 部署约 **11 个容器** |
| 许可 | Frappe **MIT**；ERPNext **GPLv3** |
| 接口 | REST（`/api/resource/<DocType>`、`/api/method/...`）+ API Key/Secret、Webhook、Server Script |
| 强项 | **总账/复式记账（GL Entry）、AR/AP、税务、多币种、多公司、成本核算、财务合规**；制造（BOM/MRP/工单）、HR、CRM、网站 |
| 弱项 | 中文本地化体感、Windows 单机分发、手机端离线、本地 OCR、轻量快速上手 |

### ⚠️ 三个必须先认清的分歧

**1. 单据语义分歧（最根本）**
- **ERPNext**：库存由 `Stock Ledger Entry` 驱动，财务由 **`GL Entry` 双分录**驱动 —— **会计凭证是事实源**，业务单据只是触发器。
- **我们**：业务单据直接写自己的流水表（`inventory_transactions` / `financial_transactions`），**没有复式记账、没有科目、没有总账**。

> 这不是"字段映射"能解决的，是**两种记账哲学**。把它磨平 = 重做账务内核。

**2. 部署形态分歧**
- 你现在：**Windows 单机 exe + 局域网手机 PWA**，双击即用、零运维。
- ERPNext：**Linux + Docker + MariaDB + Redis + nginx**，11 个容器起步，需要专门的运维。

**3. "插座"设计的落差**
- 我们的 6 个注册表是**手写的插件点**；ERPNext 的 **DocType + hooks + Custom Fields + Server Scripts** 是同一思路的**超集**。
- 所以"把插座融进 ERPNext"这件事，**不是升级，是降级** —— ERPNext 原生就有更强的元数据机制。

## 四、三条融合路径的可行性

### 路径 A：整体迁到 ERPNext（换底座）

| 项 | 评估 |
|---|---|
| 数据迁移 | ✅ **半天**。Data Import 导 CSV 即可（348 条主数据 + 42 行期初） |
| 功能对齐 | ⚠️ **数周~数月**。要重建：浩技云式 51 菜单体感、20 种打印模板的中文版式、期初建账口径、组合拆卸、报损报溢等 |
| 账务对齐 | ⚠️ **最重**。要把"流水表"思维换成"GL Entry 双分录"，等于重新设计账务 |
| 交付形态 | ❌ **会丢失**：Windows exe、局域网 PWA、鸿蒙工程 |
| 附加成本 | ❌ Windows 上跑 ERPNext 要先上 WSL2/Docker；PG→MariaDB 要么换库要么赌非官方支持 |
| 许可 | ⚠️ GPLv3 有传染性（内部使用无碍；对外分发需开源） |

**结论：数据上可行，但等于用 ERPNext 重做一遍，且丢掉现有交付优势。**

### 路径 B：把我们的特色设计移植进 ERPNext

- 6 个插座 → ERPNext 原生 DocType/hooks 已覆盖且更强，**移植无意义**
- 值得移植的只有两样：**余额口径（收付实现制）** 与 **base64 JSON 二进制通道**（后者在 ERPNext 里用原生文件接口即可，也不需要）

**结论：不建议。方向反了。**

### 路径 C：两者并存 + 数据互推

| 项 | 评估 |
|---|---|
| 接口 | ✅ ERPNext REST API 成熟，Token 鉴权，能做单据级 CRUD |
| 数据量 | ✅ 极小，同步压力可忽略 |
| 主数据一致性 | ⚠️ 商品/客户/供应商**双份维护**是长期成本（谁是主？） |
| 单据语义映射 | ⚠️ 仍需把"我们的一张销售单"映射成"ERPNext 的 Sales Invoice + Stock Entry + GL Entry"，是持续的对账工作量 |
| 运维 | ⚠️ 多一套 Linux/Docker 要养 |

**结论：技术上可行，但"双份主数据 + 语义映射"是长期负担；只有在**确实需要 ERPNext 的专业账务/税务**时才划算。**

## 五、我的建议

### 先问清楚"融合"到底要解决什么

| 你的真实目的 | 该走的路 |
|---|---|
| 少写代码、要一个成熟 ERP | **路径 A**，但接受 Linux/Docker/MariaDB + 放弃 Windows 分发 |
| 拿到 ERPNext 最强的**总账/复式记账/税务** | **不迁移** —— 照它的模型给现有系统**加一层总账**（见下） |
| 两边都要、各用所长 | **路径 C**，但先定"主数据以谁为准" |
| 只是评估，暂不动 | 保持现状 + 做下面这件事 |

### 最划算的动作：借它的**账务模型**，而不是借它的**代码**

你现在**最缺的不是功能页，是总账**：14,146 行后端里没有科目表、没有凭证、没有试算平衡、没有报表勾稽。
而这恰恰是 ERPNext 二十年沉淀最厚的地方。

建议照它的模型，在现有系统里补一层（**不动任何现有单据**）：

1. **科目表**（`accounts`：资产/负债/权益/收入/费用，支持父子级）
2. **凭证 + 分录**（`journal_entries` + `journal_entry_lines`，借贷双分录，**凭证是事实源**）
3. **自动过账规则**：现有 `DOC_TYPES` 的 24 种事件各配一条"借什么/贷什么"，挂在已有的"审核后自动写流水"那个钩子上
4. **三张基础报表**：科目余额表、明细账、试算平衡

**成本**：可控（一个批次级）。**收益**：把"流水台账"升级成"能对外交代的账"，同时**完全保留** Windows 分发 / 手机 PWA / 本地 OCR / AI 助手这些 ERPNext 给不了的东西。

### 如果就是想上 ERPNext：第一步做什么

1. **先用 Docker 起一个 ERPNext 站**（WSL2 或 Linux 服务器），**不迁任何数据**
2. 拿**真实场景**试三件事：① 期初 42 行能不能导进去且账实相符 ② 一张销售单走完出库+开票+收款，看 GL Entry 长什么样 ③ 打印出来的中文单据能不能达到你现在 20 个模板的水准
3. 这三件里有一件过不去，就说明整体迁移的代价超出预期 —— **先花 1~2 天验证，比先花两周迁数据划算**

## 六、一句话回答

> **数据可以融（量太小了，半天的事）；代码不该融（两套哲学，融了等于重做）；**
> **能融、且值得融的，是 ERPNext 的「复式记账 / 总账 / 税务」这一层账务模型 ——**
> **把它搬进现有系统，比把现有系统搬进 ERPNext，代价小一个量级、收益也更直接。**

你现在的真实短板是**账务深度**，不是功能数量：
51 个菜单已全部实装、386 条测试全过，但 33 张表是空的、没有总账。
**下一步该补的是"钱的账"，而不是"更多页面"。**
