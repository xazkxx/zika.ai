# 二、ERPNext 的模型骨架：它的严格性从哪来

ERPNext 有 20 年沉淀，但**真正值得借的不是它的功能数量，是它的一个设计信条**：

> **派生数据不可手改，一律由事实源推导出来。**

具体落成五个抽象：

| # | 抽象 | 作用 |
|---|---|---|
| 1 | **DocType** | 表 = 表单 = 权限 = 工作流，元数据驱动，加字段不改代码 |
| 2 | **docstatus 三态 + 不可变** | 草稿(0) / 已提交(1) / 已取消(2)。**提交后不可修改**，要改只能取消重开（amend） |
| 3 | **GL Entry 复式记账** | 会计凭证是**财务的事实源**；应收应付、成本、税全部由它推导 |
| 4 | **Stock Ledger Entry + valuation rate** | 库存流水是**库存的事实源**，带成本层（FIFO / 移动加权），出库自动结转成本 |
| 5 | **Company / Cost Center / Fiscal Year** | 组织、维度、期间三个正交坐标；**已关账期间不可过账** |

**我们的系统是另一套信条**：每个页面直接写自己的表，派生值（余额、库存、毛利）**当场算、当场存**，没有统一的事实源。

这套做法**上手快、代码短**——这就是为什么 51 个菜单能在 17,900 行前端里全部实装。
但代价是：**同一件事只有一个地方算得对，换个入口就可能有第二套算法**。

# 三、逐项体检表

分四档：🔴 根本性差距（不补会出错）· 🟠 高（合规/可追溯刚需）· 🟡 中（值得借）· ⚪ 不必借。

## 🔴 一档：根本性差距

### 3.1 账务内核：单式流水 vs 复式记账

| | 我们 | ERPNext |
|---|---|---|
| 事实源 | `financial_transactions`（13 条），按 `transaction_type` 分 24 种事件 | `GL Entry` 双分录 |
| 科目表 | **没有** | Chart of Accounts（树，支持父子级） |
| 凭证 | **没有** | Journal Entry |
| 试算平衡 | **没有** | 内建；借贷不等直接报错 |
| 报表 | 业务口径的汇总页 | 科目余额表 / 明细账 / 三大报表 |

**实测证据**：全库搜不到 `Account` / `JournalEntry` / `debit` / `credit` / `trial_balance`
的任何实现（唯一命中"试算"的是 MRP 的**物料需求试算**，与会计无关）。

**后果**：现在的"账"是**流水台账**，不是能对外交代的账。没有科目就没法出资产负债表/利润表，
也没有"借贷是否相等"这个唯一能证明"账做对了"的自检。

→ **建议：借。** 这是最值得做的一件，也是原方案第 15 批的内容。代价可控（一个批次级），
且**不动任何现有单据**——只在"单据审核后自动写流水"那个钩子旁边多挂一次 `post_journal()`。

### 3.2 库存成本：静态价 vs 成本层

| | 我们 | ERPNext |
|---|---|---|
| 出库成本 | `_resolve_cost_price()` → **商品档案的 `purchase_price` 静态字段** | Stock Ledger Entry 的 valuation rate |
| 成本法 | **无** | FIFO / 移动加权平均，可配置 |
| 结账后重算 | 无 | Repost Item Valuation |
| 成本结转 | **销售出库不结转成本**（只有成品入库结转了生产成本） | 出库自动生成 COGS 分录 |

**实测证据**：
- `_resolve_cost_price(db, product_id, given)` 的实现就是"没填就取 `Product.purchase_price`"；
- 全库搜不到 `主营业务成本` / 销售出库的成本分录。

**后果**：
- **毛利是估的**——用"卖价 − 商品档案里填的进价"，而不是这批货实际买进来的价格。
  同一商品今年买两次、价格不同，系统分不出来；
- 库存金额 = 数量 × 档案进价，**不是库存的真实成本**。

→ **建议：借，但取最简形态。** 不必上完整 FIFO + 重算，先做**移动加权平均**：
每一次入库更新商品在该仓库的加权成本，出库按当前加权成本结转。
这是小企业最常用、也最不容易吵起来的做法。**没有它，利润表出来也不能信。**

### 3.3 单据状态：没有统一的状态机，也没有流转校验

| | 我们 | ERPNext |
|---|---|---|
| 状态载体 | 每个单据各自的 `status` 字符串（`draft`/`submitted`/`cancelled`…） | 统一的 `docstatus` 0/1/2 |
| 流转校验 | **无**。`PATCH /sales-orders/{id}/status` 直接 `item.status = status_value` —— 任意状态可跳到任意状态 | 只能按定义的 transitions 走 |
| 撤销副作用 | 删除单据有反冲（`_revert_stock` / `_revert_finance` ✓），但**改状态不会** | cancel 自动反冲所有派生记录 |
| 字段级修改 | 有 PATCH 的单据（发票 / 合同 / 报价单）在业务发生后**仍可改字段**，且无字段级痕迹 | 提交后锁定，只能取消重开 |

**实测证据**：
- `update_sales_order_status()` 全文只有"取 payload.status → 赋值 → commit"，**没有任何合法流转校验**；
- 销售单/采购单只有 `.../status` 这一个 PATCH 接口，没有通用字段更新接口（这点是好的）；
- 业务表（`sales_order` / `invoice` / `product`）**都没有** `owner` / `modified_by` 字段。

**后果（举一个真会发生的场景）**：
一张已提交、已出库、已写应收的销售单，把状态从 `submitted` 改回 `draft` ——
**库存流水和财务流水都还在**，但单据显示为草稿。账与单据就此脱节，而且**没有任何痕迹**。

→ **建议：借。** 给状态流转加一张合法转移表（`draft → submitted → cancelled`，
已提交禁止回退；要改就"取消 → 红冲 → 重开"）。这是"账能与单据对上"的地基。

## 🟠 二档：合规与可追溯刚需

### 3.4 期间关账

| | 我们 | ERPNext |
|---|---|---|
| 会计期间 | `financial_transactions.period`（`YYYY-MM`，**已建索引**） | Fiscal Year + 按月/季/年关账 |
| 关账动作 | **完全没有** | Period Closing Voucher；已关账期间拒绝过账 |

**实测证据**：`period` 字段存在且有索引，但全库搜不到任何"关账 / 锁账 / 期间锁定"逻辑。

**后果**：上个月的账报出去了，这个月还能往上个月插一笔。**期间数字会变，报表失去意义。**

→ **建议：借。** 一张 `closed_periods` 表 + 过账时校验，几十行代码，但这是"能报税"的前提。

### 3.5 审计追踪：谁改了什么值

| | 我们 | ERPNext |
|---|---|---|
| 有 | `operation_logs` 5,174 条（中间件记录：谁、什么时候、哪个接口、状态码） | owner / creation / modified / modified_by + **Version 表（字段级 diff）** |
| 缺 | **改了哪个字段、从什么改成什么** | 全都有 |

**实测证据**：业务表（`sales_order` / `invoice` / `product`）**都没有** `owner` / `modified_by` 字段。

→ **建议：借一半。** 给核心单据（订单/出入库/发票/凭证）加 `modified_by`，
改动时把"字段 → 旧值 → 新值"写进一张 `record_versions` 表。
报表数据被人改了却查不出改了什么，是审计过不去的。

### 3.6 权限粒度：页面级 vs 行级

| | 我们 | ERPNext |
|---|---|---|
| 粒度 | **菜单页面**（权限点＝页面，固定清单） | DocType + 角色权限 + **User Permission（行级，可按仓库/公司/成本中心）** |
| 设计说明 | 刻意不做按钮级/字段级（见 `core/permissions.py` 的论证） | 全都有 |

**多账套落地后这条必须重看**：账套隔离（schema）解决的是"公司之间"，
但**同一家公司内部**仍有"仓管只能看自己仓库"的真实需求 —— 现在做不到。

→ **建议：借一个最小维度。** 给 `user_companies` 加"可访问仓库"，
在库存/单据查询上加一层过滤。**不做**通用行级权限引擎（那才是过度设计）。

| # | 项 | 我们 | ERPNext | 建议 |
|---|---|---|---|---|
| 3.7 | **合并报表** | 刚做多账套（一账套一 schema），**跨账套汇总还没有** | 单库 `company` 字段，合并报表原生 | **借**（用户明确要"老板看集团总数"）。用跨 schema `UNION ALL` 做，条子清净好做 |

| 3.12 | **命名序列** | ✅ `_next_doc_no()` 后端生成（`XS20261013001`） | Naming Series（可配置前缀+期间+序号） | 现状够用，不借 |

## ⚪ 四档：明确**不**借（避免过度设计）

| 项 | 为什么不借 |
|---|---|
| **换 ERPNext 底座** | 见 `erpnext融合可行性评估.md`：两套记账哲学，融了等于重做；且会丢掉 Windows 单机 exe、局域网 PWA、鸿蒙、本地 OCR 这些它的给不了的东西 |
| **DocType 元数据引擎** | 我们的"6 个插座"（财务事件/库存溯源/打印/Excel/菜单/权限）已覆盖实际需求；做通用元数据引擎是拿一个大工程换一个还没出现的需求 |
| **可视化工作流引擎** | 状态机是硬编码枚举，但业务只有 3~5 个状态、流程不常改。用配置引擎换来的灵活性，抵不过复杂度 |
| **多币种 / 汇率** | 三家公司都在境内、都用人民币。除非有外贸业务，否则是纯粹的负担 |
| **自定义字段（Custom Field）** | 同上：需求未出现 |

> 判断标准很简单：**ERPNext 的每个抽象都在解决"规模"问题**（多公司、多币种、多维度、多角色）。
> 你们是 3 家公司、几十个用户、几千条单据 —— 借它的**信条**（派生数据由事实源推导），
> 不要借它的**规模装置**。

# 四、改造建议（按批次）

## 第一批：把"账"做对（P0）

| 项 | 内容 | 为什么排第一 |
|---|---|---|
| 1 | **总账**：科目表 / 凭证 + 分录 / 过账规则 / 科目余额表·明细账·试算平衡 | 现在没有"能对外交代的账" |
| 2 | **库存成本层**：移动加权平均 + 出库结转成本 | 现在毛利是估的 |
| 3 | **期间关账**：已关账期间拒绝过账 | 否则期间数字会变 |
| 4 | **单据状态机**：合法流转表 + 已提交不可回退 + 取消即反冲 | 否则账与单据会脱节且无痕 |

**顺序有讲究**：2 依赖 1（成本结转要生成分录），3 和 4 都挂在 1 的过账钩子上。
所以**先做 1，再 2，然后 3、4**。

## 第二批：多账套的收尾（P1）

| 项 | 内容 |
|---|---|
| 5 | **合并报表**：跨账套汇总（总销售额/总利润/各公司对比）—— 用户已明确要 |
| 6 | **公司间调拨**：唯一需要跨 schema 事务的功能；**税务上按销售处理**（确认收入+结转成本+开票），绝不能用同公司调拨那套"不写财务流水" |
| 7 | 会计维度补**部门（成本中心）** |
| 8 | 权限补**按仓库行级**过滤 |

| 项 | 内容 |
|---|---|

# 六、一句话结论

> **不该借它的代码，也早就论证过；这次体检的真正发现是——**
> **有两处"根本性差距"是必须补的：一是没有总账（单式流水），二是没有成本层（毛利是估的）。**
> **这两条不补，系统再多个页面也不能用来算利润、报税。**
>
> 其余的（多币种 / 自定义字段 / 工作流引擎 / 元数据引擎）**都是 ERPNext 为解决"规模"而生的装置，
> 对 3 家公司、几千条单据的体量是负担，不必借。**
>
> 而**最该立刻做的、与架构无关的那件事**：33 张表零数据 ——
> 先挑 4 张最常用的走通完整一单，把"写完"变成"能用"。
