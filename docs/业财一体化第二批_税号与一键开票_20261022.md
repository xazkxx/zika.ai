## 二、供应商税号（tax_no）

### 1. 列怎么加的（幂等、可空、不锁表）

```python
# app/models/supplier.py
tax_no: Mapped[str | None] = mapped_column(String(50), nullable=True)

# app/main.py —— SUPPLIER_ADDITIONS **只追加键**，不整体重赋值
SUPPLIER_ADDITIONS = { ..., "tax_no": "VARCHAR(50)" }
```

启动时 `_add_missing_columns` 自动 `ALTER TABLE ... ADD COLUMN`，老供应商留空、不阻塞任何历史数据。
（口径与 `Customer.tax_no` 完全一致：同长度、同可空。）

### 2. 三处 UI 都到位

| 位置 | 改动 |
|---|---|
| 新增/编辑供应商弹窗 | 名称下方整行「纳税人识别号」，placeholder 写明"进项发票上的销售方识别号" |
| 供应商列表 | 新增「纳税人识别号」列，**空值显示「未登记」**（一眼看出谁还没补） |
| 发票编辑弹窗 | 买方/卖方税号本来就输入框，但见下面「4. 顺手修的一个静默 bug」 |

### 3. 匹配改成「税号优先、名称兜底」

```python
# app/services/invoice_match.py
def _resolve_supplier(db, invoice):
    # ① 税号唯一命中（税局发的唯一标识，OCR 认它的准确率也高于名称）
    tax = _normalize_tax_no(invoice.seller_tax_no)
    if tax:
        hits = [r for r in db.query(Supplier).filter(Supplier.tax_no.isnot(None)).all()
                if _normalize_tax_no(r.tax_no) == tax]
        if len(hits) == 1:
            return hits[0].id, hits[0].name or ""
    # ② 名称归一化**全等**兜底（不做包含：'XX公司' 包含于 'XX公司第一分公司'，按包含判必错）
    ...
```

销项侧（`_resolve_customer` 与 `_resolve_customer_id`）同步改成税号优先 ——
否则会出现"进项认税号、销项认名称"两套逻辑，同一张票换个方向结论就变。

税号命中**多家**（同一税号挂多档案，库里真实存在 #705/#709/#714）一律视为歧义、退回名称，**不猜**。

### 4. 顺手修的一个静默 bug（很重要）

发票弹窗里一直有「买方税号 / 卖方税号 / 发票号码」输入框，前端也一直在提交，
但 `InvoiceUpdate` **没有这几个字段** —— Pydantic 默认忽略未声明字段，于是：

> 改税号 → 点保存 → 界面刷新回原值，**一声不响**。

现在补进 schema，并给 `invoice_no` 加了唯一性校验（撞号 → 409，不许静默顶掉别人的票；
真实场景里 OCR 抄错一位就会撞）。同时支持改 `issue_date / counterparty_name / buyer_name / seller_name / invoice_code`。

### 5. 存量税号：现在是 1/63，需要补

```
供应商 63 家，已有税号 1 家
客户   28 家，有税号 6 家
```

税号匹配要真正生效，得先把税号填进去。两条路：

- **手工**：供应商档案列表里「未登记」那一列，逐个点编辑补（弹窗已就位）；
- **回填脚本**：`scripts/backfill_supplier_tax_no.py` —— 按"进项发票的销售方税号"回填。
  只填空值、只认唯一、同名多家跳过，默认**只预演**：

```bash

python scripts/backfill_supplier_tax_no.py --apply  # 确认后落库
```

> 等进项票开始录入，这个脚本就能一键补齐。

## 三、销售单「一键开票」（先销后票）

### 1. 一条命令完成三件事

```http
POST /api/v1/sales-orders/{order_id}/issue-invoice
{ "invoice_no": "可选", "total_amount": 可选, "invoice_type": "普票", "issue_date": "可选" }
```

服务端做的是：

| 项 | 取值 | 为什么 |
|---|---|---|
| 金额 | 未开票余额（可传更小的值做分次开票） | 不让人手填，填错就骗过完结闸 |
| 明细 | 单据明细逐行搬（`item_name/spec/unit/quantity/unit_price/amount`） | 与 OCR 解析同款结构，打印/导出不用开分支 |
| `related_order_id` | **当场挂上** | 完结闸与四流底稿只认它 |
| 票号 | 不传 → `KP-<单号>`（撞号自动 `-2/-3`） | 真实票号在税控平台出票后才拿得到，不能卡着不让登记 |

### 2. 四条约束（都是防"票开了但对不上账"）

```python
if order.status == "cancelled":           409 "已作废，不能开票"
if not items:                             400 "这张单没有明细，无法开票"
if remaining <= 0.005:                    409 {code: "already_invoiced"}  # 已开齐，防重复开
if amount > remaining + 0.01:             400 "超过未开票余额，请拆成多次或改小金额"
if invoice_no 已存在:                      409 "同号会被当成换票"
```

### 3. 前端：详情页多了一个主按钮

```
[收款]  [一键开票]  [登记票号]  [标记为已完结]
           ↑ 新增（primary，未开票为 0 时自动置灰 + title 说明原因）
```

- 「一键开票」= 不弹窗、直接生成（票号占位，提示"拿到真实票号后到发票管理里改"）；
- 「登记票号」= 原来的弹窗，保留给"要精确录真实票号/分次开票"的场景；
- 成功后**关掉抽屉并重拉列表**：`settled` / `uninvoiced_amount` 都是后端算的，
  前端不复算（复算必然出现"前端说能完结、后端 409"的两张皮）。

### 4. 为什么票号可以留空（这是我刻意做的取舍）

系统没接税局数电平台，票号只能等出票后才知道。若强制填票号，业务就会把
"货已发、款已收、票在开"的单子一直挂在「未开票」，完结闸永远拦着 —— 那是更坏的结果。
所以：**生成记录 + 占位号 + 明确提示后补**，把"业务已发生"和"票号已录入"解耦。

## 四、⭐ 期间发现的大问题：完结按钮其实一直是灰的

跑第二遍验收时，`一键开票` 按钮一直是 disabled，查下去发现更深的问题：

**`settled` / `uninvoiced_amount` / `outstanding_amount` / `invoiced_amount` 这四个字段，
后端根本不返回。** 它们的实现（`_apply_settlement_fields`、`_invoiced_amounts_by_order`）
只存在于 `erp_sales.py.bak-1020124407` 这份备份里，主文件在 10-12 那次回滚中丢了。

后果链：

```
列表不返回 settled → 前端 canComplete = Boolean(detailRow?.settled) 恒 false
                   → 「标记为已完结」按钮**永远灰着**
                   → 而且没有任何报错，用户只会觉得"这功能没做完"
```

之前 E2E 之所以全绿，是因为**完结那一步走的是接口**（`PATCH /status` 服务端照常校验），
UI 层这条断链被完美掩盖了。

已按原口径恢复，并统一到「与完结闸同一公式」：

```python
def _apply_settlement_fields(payload, invoiced=0.0):
    receivable = float(payload.receivable_amount or 0) or float(payload.total_amount or 0)
    net = round(receivable - float(payload.discount_amount or 0), 2)
    outstanding = round(net - float(payload.received_amount or 0), 2)
    # ⚠️ 未开票刻意用 total_amount（不是净额）：服务端拦完结时算的就是 total − 已开票
    uninvoiced = round(max(0.0, float(payload.total_amount or 0) - float(invoiced or 0)), 2)
    payload.invoiced_amount, payload.outstanding_amount, payload.uninvoiced_amount = ...
    payload.settled = outstanding <= 0.005 and uninvoiced <= 0.005
```

**新增两条用例把它钉住**：
`test_list_exposes_settlement_fields`（新单四个数都对）、
`test_settled_requires_both_money_and_invoice`（只开票不收款 / 只收款不开票都必须 false，
两个都清才 true，并且服务端确实放行完结）。

> 这条如果你要"当场看见"：8019 上随便挑一张有欠款的出库单点预览，
> 底部「结算：应收余额 ¥x · 未开票 ¥y」现在有数了，收齐+开齐后「标记为已完结」会自己亮。

## 五、清理链又补了两个洞（都是这轮实测到的）

1. **孤儿发票**：`一键开票` 生成的 `KP-<单号>` 是**真实业务数据**，不能按票号签名删。
   判据改成"指向的销售单/入库单已经不存在"（与票号形态无关，生产库跑也只删真坏掉的）。
2. **孤儿发票流水**：发票同步到财务会写一条 `expense`（备注「发票 <票号> | …」），
   票删了流水还在，会把「日常收支」合计撑大。改成"票号在 invoices 里不存在就删"。

本轮实测：孤儿发票 19 张 + 孤儿流水 15 条，已清；再跑一轮 pytest 后仍是 6 张票 / 81 条流水。
