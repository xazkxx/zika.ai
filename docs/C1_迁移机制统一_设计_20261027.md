# C1 迁移机制统一 · 设计确认稿（2026-10-27）

> 状态：🚧 初版已落地（`app/db/migrations.py` + 启动接入 + 单测），后续批次往里搬迁移
> 依据：《首屏懒加载与耦合治理_20261027.md》「下一刀」第 1 条
> 一句话：把「启动时内联 DDL」「独立迁移脚本」「一次性补丁」三套并行机制，收口成
> **一个版本化迁移注册表**，让"这个库到底跑过哪些迁移"可回答、可审计、可回滚。

---

## 一、现状盘点（三套机制，精确计数）

| # | 机制 | 位置 | 规模 | 触发方式 |
|---|---|---|---|---|
| A | 内联 DDL | `app/main.py` | **17 组 `*_ADDITIONS`** + 6 处内联 `ALTER TABLE` + `_ensure_numeric_money` / `_ensure_wide_price` 转列 + `ensure_schema_in` / `ensure_contract_module` | 每次启动，幂等 |
| B | 独立迁移脚本 | `scripts/apply_phase1_migrations.py`、`migrate_*.py`、`backfill_*.py`、`reassign_history_to_companies.py` | 约 8 个 | 手工执行一次 |
| C | 一次性补丁 | `scripts/` | **80 个 `.py`**（`_patch_*`、`phase2_patch_*`、`fix_*`、`cleanup_*`、`delete_*`、`shansong_*`…） | 手工执行一次，多为历史遗留 |

另有 `migration/scripts/` 6 个（`haoji_*`、`import_offers.py`）：**数据导入**脚本，
不是 schema 迁移，本批**不收**进注册表（数据导入要能反复跑、能重放，语义不同）。

### 三套并行的三个后果

1. **无法回答"这个库跑过哪些迁移"**：A 靠 `has_table` / `get_columns` 现查现补，B/C 无任何记录；
2. **同一列可能被两套机制各补一次**：A 幂等补列，B/C 里可能又有同款 `ALTER`；
3. **一次性补丁不可审计**：散落 80 个文件，没有执行顺序、没有"跑没跑过"的状态。

---

## 二、目标

一个**版本化迁移注册表**，满足：

1. **有记录**：`erp_migrations` 表（public + 各账套 schema 各一份）记下每个已跑迁移的 id + 名字 + 时间；
2. **有顺序**：迁移按 id 升序执行，只增不改（已发布条目改 id/内容会让老库状态错乱）；
3. **可回滚**：每个迁移与"记录它已跑"在同一事务，抛异常整条回滚（不会半途）；
4. **多账套一致**：public 与每个账套 schema 各自维护一份迁移历史，与现有 `ensure_schema_in` 同口径。

## 三、新机制设计（最小实现，不引入 Alembic）

### 3.1 核心：`app/db/migrations.py`（已落地）

```python
MIGRATIONS: list[tuple[int, str, object]] = []   # (id, name, upgrade) 注册表

def apply_pending(engine) -> list[int]:
    """按 id 升序跑「还没跑过」的迁移，返回本次新应用的 id 列表。"""
    # 1. CREATE TABLE IF NOT EXISTS erp_migrations(id, name, applied_at)
    # 2. SELECT 已跑 id
    # 3. 跳过已跑，逐个 upgrade(conn) + INSERT 记录（同一事务）
```

- 幂等由「已跑过就跳过」保证，不要求每段 SQL 自己 `IF NOT EXISTS`；
- 事务边界：`engine.begin()` 包裹「跑迁移 + 写记录」，upgrade 抛异常整条回滚。

### 3.2 启动接入（已落地，空注册表时是 no-op）

| 位置 | 调用 | engine |
|---|---|---|
| `create_app()` | `apply_pending(engine)` | 默认 engine（public） |
| `ensure_all_tenant_schemas()` | `apply_pending(ddl_engine_for(schema))` | **不带 public**，避免 `has_table("erp_migrations")` 误判成 public 的表 |

> 为什么账套必须用 `ddl_engine_for`（search_path 不带 public）：`has_table` 按 search_path
> 解析，带 public 时若账套还没有 `erp_migrations`，会先找到 public 里那张、把 public 的
> 迁移历史误当成账套自己的 —— 那是串账。与 `create_tenant_tables` 用同一把引擎。

### 3.3 约束（写死）

- **C1 完成前不删** `*_ADDITIONS` / `ensure_schema_in` / `ensure_contract_module`：
  旧机制继续兜底，新机制先接管「新增迁移」，验证通过后再搬旧条目、最后才删旧机制。
