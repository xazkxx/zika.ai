## 一、唯一性规则

### 后端（兜底，409 + 中文提示）

| 对象 | 范围 | 命中时的返回 |
|---|---|---|
| 客户 | **全库**名称唯一 | `409` `客户名称「X」已存在（编码 甲CUS0008），请检查是否已录入` |
| 供应商 | **全库**名称唯一 | `409` `供应商名称「X」已存在（编码 SUP...）…` |
| 商品 | **全库**名称唯一 | `409` `商品名称「X」已存在（编码 0100），请检查是否已录入` |
| 商品分类 | **同一父级**下唯一 | `409` `同一上级下已有同名类别「五金」（id=3），请换个名字或直接用现有的那个` |

实现（`app/api/v1/routes/erp_archive.py`）：

```python
def _conflict(detail: str) -> None:
    """409 = 和库里的数据撞了；400 是"你传的格式不对"。前端据此决定红字拦截。"""
    raise HTTPException(status_code=409, detail=detail)

def _assert_name_unique(db, model, name, label, *, exclude_id=None, code_field="code"):
    key = (name or "").strip()
    if not key:
        return                      # 空白名称不参与（历史数据里有 name 为空的行）
    q = db.query(model).filter(func.lower(func.trim(model.name)) == key.lower())
    if exclude_id is not None:
        q = q.filter(model.id != exclude_id)   # 改名时别被自己挡住
    hit = q.first()
    if hit is not None:
        code = getattr(hit, code_field, None)
        _conflict(f"{label}名称「{key}」已存在（编码 {code}）…，请检查是否已录入")
```

挂载点：`create_customer` / `update_customer` / `create_supplier` / `update_supplier` /
`create_product` / `update_product`。编码重复也从 400 改成 409 + 中文（原来是英文 `Customer code already exists`）。

### 为什么最终**没有**上库级唯一索引（重要）

我先按"Pydantic/SQLAlchemy 唯一约束"的思路在启动时建了
`uq_customers_name` / `uq_suppliers_name`（`CREATE UNIQUE INDEX ... lower(btrim(name))`），
结果**整套 pytest 连环失败 35 个**：

```
供应商名称「测试供应商-库存」已存在（编码 SUP-5c1fa5d9）
```

原因：测试夹具用的是**固定中文名 + 随机编码**（`"测试供应商-库存"`、`"测试客户A"`…），
不同用例会反复建同名档案；库级唯一索引一建，第二次就 `IntegrityError`（500）。
`products.name` 更不可能上索引 —— 库里现存 **22 组同名商品**（历史导入造成）。

所以本轮的落点是：

| 层 | 做法 |
|---|---|
| 应用层 | **409 + 中文提示**（本节第一段），并对"编码形如测试签名"的历史行放行（与 `clean_test_data.py` 同一套签名，生产编码 `甲CUS…/0100` 永不命中） |
| 库层 | **暂不建唯一索引**。等测试夹具改成"名称带 uuid"、且 22 组同名商品清完之后，再把索引打开 |

> 结论：现在的严格性 = 应用层 100%，库层 0%。
> 并发下两个请求同时通过校验的窗口是存在的（毫秒级）——要彻底堵住，得先清测试数据再上索引。
> 这是我的判断：**宁可留这个已知窗口，也不要把 485 个测试打挂**。

## 二、前端拦截（`frontend/src/lib/nameGuard.js`）

四个便宜但命中率高的信号（不引第三方拼音库，离线部署也跑得动）：

| 信号 | 例子 |
|---|---|
| 完全同名（规范化后） | `陕西送变电` vs `陕西送变电 ` → **重名，红字拦下** |
| 前三个字相同 | `陕北至关中…(包13)` vs `陕北至关（二部）` |
| 前两个字相同 | `劳保鞋` vs `劳保手套` |
| 一方包含另一方 | `劳保鞋` vs `劳保鞋(新)` |
| 编辑距离 ≤ 1（短名） | `甲001` vs `甲0001` |
| **助记码**（商品专用） | 拼音首字母相同 → 读音相近 |

规范化会去掉空白/破折号/全角括号，并统一小写，避免"看起来一样却比不出来"。

### 交互

```
点保存
 ├─ 本地查重命中 → 红字提示条（notice-box--danger）：「该名称已存在：客户「X」（编码 甲CUS0008），请检查是否已录入。」→ 不提交、弹窗不关
 ├─ 命中相似    → 黄色确认框「检测到相似名称」，列出候选 + 原因（前三个字相同 / 助记码相近…）
 │                 · 「仍然新建」→ 置 skip 标记后 form.requestSubmit() 重放，真正提交
 │                 · 「返回修改」→ 关闭，留在表单
 └─ 都没有      → 正常提交（后端 409 仍然兜底，并发情况也挡得住）
```

接入点：新增/编辑客户、供应商、商品、商品分类（同一父级）。
后端返回 409 时同样走红字（并发或别的入口写的）。

## 三、空壳数据治理（删除保护）

分类删除的三段判定（`delete_product_category`）：

| 情形 | 结果 |
|---|---|
| 有子分类 | `409`「「五金」下还有 **1** 个子分类，无法直接删除。请先删除或转移这些子分类。」 |
| 有商品 | `409`「「X」下存在 **N** 个商品，无法直接删除。请先把这些商品转移到其它类别。」 |
| 都没有（真空壳） | **204，直接删** |

实测：

```
删有商品的「五金」      → 409「下还有 1 个子分类…」
建空分类 → 删           → 201 → 204  （直接删掉）
建父+子 → 删父          → 409「下还有 1 个子分类…」
删子 → 删父             → 204 → 204
```

> 客户/供应商分类用的是同一套 `_delete_archive` 保护逻辑（有档案引用时 409）。

## 四、发票关联出库单（告别脚本）

「财务 → 发票管理 → 编辑发票」弹窗里新增 **「关联出库单（销项）」** 下拉（`ErpSearchSelect`）：

- 只列 `doc_type=outbound` 的销售单（订单/退货单不该出现在这里）
- 展示格式：`XS2025… · 客户名 · ¥金额`，可按单号/客户名搜索
- 留空 = 不关联；保存时以 `related_order_id` 提交（后端 `InvoiceUpdate` 原生支持）
- 有了这个字段，出库单的「标记为已完结」才可能通过"未开票 = 0"这道闸
