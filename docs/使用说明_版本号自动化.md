# 使用说明：版本条与构建标识（全自动）

> 面向：日常使用者 + 负责发版的同事
> 更新：2026-10-19（版本号改为构建时自动递增，不用再手改任何文件）

---

## 一、侧边栏那一行字是什么

系统左上角（手机端在菜单抽屉里）显示一行小字：

```
v52 · 2026-10-19 17:15 · 寨卡
```

三个数字各有用处，**出了任何"我明明改了却没生效"的疑问，先看这一行**：

| 段落 | 含义 | 怎么变 |
|---|---|---|
| `v52` | **缓存代号**，第 52 代前端外壳 | 每次 `npm run build` 自动 +1 |
| `2026-10-19 17:15` | 这次构建的**时间**（精确到分） | 每次构建自动取当前时间 |
| `寨卡` | 品牌名 | 固定，换品牌改一处（见第四节） |

鼠标悬停能看到更全的信息：业务版本、缓存代号、构建时间、代码提交号。

### 为什么要有"缓存代号"

系统是装在浏览器里用的（PWA），浏览器会把页面外壳缓存下来，断网也能打开。
如果新版本发下去、这个号却没变，浏览器会认为"还是原来那个"，**继续显示旧页面** ——
你会以为更新失败，其实是浏览器没换壳。所以这个号**必须每次 +1**，而且**只增不减**。

## 二、以后怎么发版（比以前少一步）

以前要手改两处：`package.json` 的版本号 + `sw.js` 的缓存代号，漏一处就出鬼。

现在只要一条命令：

```bat
cd /d E:\AI\ERP软件\frontend
npm run build
```

它会自动做完三件事：

1. 把 `public/sw.js` 里的缓存代号 +1（v51 → v52）；
2. 把当前时间做成构建时间；
3. 生成 `dist/version.json`，让后端和 exe 也能读到同一个号。

**不用再手改任何文件。** 改完刷新页面，那行小字就会变成新的号。

> 开发模式（`npm run dev`）**不会**加号，只有正式构建才加 —— 否则边写代码边热更新，
> 缓存代号会一路飞走。

---

## 三、怎么确认"我看到的确实是刚打的那一版"

三步，30 秒：

1. 记下你构建完成的时间（命令行最后一行 `✓ built in ...`）；
2. 打开系统，看侧边栏那行字的时间是不是**这一分钟**；
3. 如果还是旧时间 → 按 **Ctrl + Shift + R** 强制刷新一次再看。

如果强刷后仍是旧号，说明浏览器拿到了旧外壳，检查：
`frontend/dist/sw.js` 里的号与 `frontend/public/sw.js` 是否一致（正常应该一致）。

## 四、换品牌名

版本条最后那段"寨卡"是**品牌名**，不是公司全称（公司全称在"公司信息"里维护，两者互不影响）。

改法二选一：

- 直接改 `frontend/vite.config.js` 顶部：`const BRAND = process.env.ERP_BRAND || '寨卡';`
- 或构建前设环境变量：`set ERP_BRAND=华诺迈` 再 `npm run build`

---

## 五、打包 exe 时要不要额外操作

**不用。** 生成的 `dist/version.json` 就在 `frontend/dist` 里，
而 `erp.spec` 本来就把整个 `frontend/dist` 打进包里，这个文件跟着走。

打包后：

- exe 启动的后端会自动读到它，`/openapi.json` 里显示 `1.0.0 (v52)`；
- 页面上显示的号与后端报的号**永远一致** —— 不会再出现"用户说页面是旧的、后端说自己是新的"这种对不上账的情况；
- 万一读不到（比如从没构建过前端），后端不会报错，只会退回 `v? · 未构建`，服务照常启动。

## 六、常见问题

**问：构建直接失败，报"读不到 public/sw.js 里的缓存代号"？**

说明 `sw.js` 里那一行被人改动过格式。它必须是这一副样子（单引号、结尾分号）：

```js
const CACHE_VERSION = 'erp-pwa-v52';
```

这是**故意的**：宁可构建当场停下，也不要"悄悄不自增"把旧外壳发出去。
把这一行改回上面格式再构建即可。

**问：我不小心连打两次包，号从 v51 跳到 v53 了，有问题吗？**

没问题。缓存代号只要求"每次发版比上次大"，跳号无害。

**问：`package.json` 里的 `1.0.0` 还要改吗？**

不用。它是**业务版本**（对外说"我们发 1.0.0"），只在发大版本时手改；
日常每次打包只动缓存代号和时间，这两项已全自动。

## 七、给维护者的技术备注（可跳过）

| 环节 | 位置 | 说明 |
|---|---|---|
| 自增 + 时间注入 | `frontend/vite.config.js` | 读 `public/sw.js` 的 `CACHE_VERSION`，`+1` 写回；同时 `define` 注入 `__APP_CACHE__` / `__APP_BRAND__` / `__APP_BUILD_AT__` |
| 清单文件 | `frontend/vite.config.js` 的 `versionManifestPlugin` | `writeBundle` 时写 `dist/version.json` |
| 前端展示 | `frontend/src/lib/appLib.js` | `APP_VERSION_LABEL = \`${APP_CACHE} · ${APP_BUILD_AT} · ${APP_BRAND}\`` |
| 展示位置 | `frontend/src/App.jsx` 侧边栏 `.brand-version` | 带 `data-app-version` / `data-app-cache` 属性，便于自动化核对 |
| 后端读取 | `app/core/build_info.py` | 开发态读 `<root>/frontend/dist/version.json`，打包态读 `_MEIPASS/frontend/dist/version.json`，读不到不报错 |
| 后端暴露 | `app/main.py` 的 `create_app()` | FastAPI `version` 与 `description` 都带构建标识 |

⚠️ 唯一仍需人工判断的事：**业务版本号**（`package.json` 的 `version`）什么时候跳到 1.1.0 / 2.0.0。
