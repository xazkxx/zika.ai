## 三、本轮抓到并修掉的 3 个**真实缺陷**

三个都是"测试跑出来的"，不是猜的。第 1 个是财务口径错，必须修；第 2 个是功能漏；第 3 个是测试会污染正式库。

### 缺陷 1（最严重）对账单「本期已开票」恒为 ¥0 —— 期末应收算错

**现象**：客户全额开票 ¥120、全额收款 ¥120，生成的对账单却是

```
本期已开票 ¥0.00     本期已收 ¥120.00     期末应收 −¥120.00
```

看起来像"客户多付了我们 120 元"。

**根因**：两张表的"方向"用了两套词表，比较永远不成立。

| 来源 | 取值 |
|---|---|
| 对账单 `direction` | `out` / `in` |
| 发票 `Invoice.direction` | `output` / `input` / `unknown` |

`app/api/v1/routes/erp_statement.py` 里原来写的是 `Invoice.direction == direction`，
`'output' == 'out'` 永远是 False —— 所以**任何客户、任何期间，本期已开票都是 0**。

**修复**（`erp_statement.py::generate_statement` 第 ② 段）：

```python
inv_direction = "output" if direction == "out" else "input"
invoice_query = db.query(Invoice).filter(Invoice.direction == inv_direction, ...)
```

**护栏**：`tests/test_statement_generate.py::test_generated_statement_full_invoice_and_receipt_nets_to_zero`
（全额开票 + 全额收款 → `receivable_balance == 0`）；E2E 里也加了硬断言：

```
PASS: STEP18 本期已开票 = ¥120（发票进了对账单）  — ¥120
PASS: STEP18 期末应收 = ¥0（开票与收款两清）  — ¥0
```

### 缺陷 2 自己开的发票进不了对账单（匹配键只有一套）

**现象**：即使方向修好了，App 里手工新建的销项发票仍然匹配不上。

**根因**：`generate_statement` 只按 `counterparty_name`（对方单位名称）匹配，而

- 历史导入 / OCR 进来的发票：只有 `counterparty_name`；
- App 内手工新建的发票：只写 `buyer_name` + `customer_id`，`counterparty_name` 是空的。

同一个文件里的"四流穿透"底稿（`_ledger_preview`）早就是
`or_(customer_id, counterparty_name)` 双口径 —— **两条路径不一致**才是真 bug。

**修复**：销项三键任一命中即算（id / buyer_name / counterparty_name），进项仍按名称（发票模型暂无 `supplier_id`）。

**护栏**：3 条用例，分别锁"只挂 id 的票"、"只挂名称的历史票"、"别的客户与区间外的票不许混进来"。

### 缺陷 3 测试清理链漏洞 —— 测试会往正式库留垃圾

**现象**：连跑几轮测试后，库里多了 **58 张 `INV-<hex>` 发票、27 张"对账测试客户xxxx"的对账单（33 行明细）**，
直接出现在「发票管理」和「对账单台账」里。更麻烦的是，一次中断的 pytest 留下的同名客户，
会让下一轮 `test_sales_return.py` **整组 5 个用例连环 409**（"客户名称已存在"）。

**根因**（三处）：

1. `clean_test_data.py` 的编码签名写死了"最多一段中段"（`CUST(-[A-Z]+)?-<hex>`），
   于是销售退货夹具的 `CUS-SRET-<hex>` 既**不被清理**、又**不被重名守卫放行**；
2. 清理脚本完全不管 `statements` / `statement_items`；
3. 发票清理只认 `TEST` / `INV-ODT-` / `INV-STATUS-`，不认 `INV-<hex>`。

**修复**：

| 文件 | 改动 |
|---|---|
| `scripts/clean_test_data.py` | 编码签名改为「`<前缀>(-<段>)* - <8位hex>`」，中段数量不限（`CUS-SRET-<hex>` / `SKU-PD-<hex>` 全认） |
| 同上 | 发票条件加 `INV-<hex>` / `DBG-<hex>` / `E2E-INV-`（真实票号是 20 位纯数字，不会撞） |
| 同上 | **新增**对账单清理：先删 `statement_items` 再删 `statements`，判据是往来单位名称含"测试客户/对账测试" |
| `app/api/v1/routes/erp_archive.py` | `_TEST_CODE_RE` 同步放宽到同一套（否则测试夹具被重名守卫拦下） |

**验证**：修完又完整跑了一轮 `pytest`，跑完自动清理，逐表核对 ——
`invoices` 回到 **6**、`statements` 回到 **4**、`statement_items` 回到 **5**，零残留。

## 四、18 步里"最容易卡住"的排名（给现场用）

排序依据是本轮真实卡住的次数（我调试时一共红了 6 次，全在这三步）。

### 第 1 名：STEP18 对账单生成 + 导出（最脆，卡了 4 次）

这一屏要连着过 **6 个环节**：切视角 → 选往来单位 → 填期间 → 生成草稿 → 按钮可用 → 文件落盘。任何一环错位都表现为"点了没反应"。

现场最容易踩的三个点：

1. **「全部」视角没有往来单位输入框**。
   默认进的是台账视角，这一屏只有一句提示"要新开一张，先切到「应收」或「应付」"。
   想新建对账单，**先点「应收」（或「应付」）页签**。
2. **「导出 Word」在没载入对账单时是灰的**，而且没有任何提示。
   正确顺序是：选好往来单位 → 填期间 → 点「生成草稿」（这时明细才出来）→ 再点「导出 Word」。
3. **别把它和右边那个"载入已存对账单"下拉搞混**。
   两个搜索框长得一样，但左边那个才是选客户的；右边那个只列**当前视角**已保存的对账单（"全部"视角下列全部）。

### 第 2 名：STEP16 发票挂出库单（卡了 2 次）

1. **页面上的出库单列表是"打开这一页时"拉的**。如果你刚在别处建了出库单，**先 F5 刷新**再进发票弹窗，
   否则下拉里根本没有新单，而且会"匹配到同号的旧单"（单号会复用，我实测挂到了 7827 那张旧单上）。
2. 下拉是挂在 `body` 上的浮层，**选项要用鼠标真实点**（它是按下就选中，不是松开才选中）。
   用键盘 Tab + 回车的路径没有测过，现场建议直接用鼠标点。

### 第 3 名：STEP3 商品辅助单位（卡了 1 次）

- 「箱 = 10」这类辅助单位必须**同时填名称和换算数**，只填一个会静默不保存（接口不报错）。
- 按钮按灰了不代表提交不了：**回车也能提交表单**。防重复提交已在代码里加了闸（`if (productBusy === 'cat') return`），
  但如果现场网络慢，仍建议点一次就等提示，别连点。

## 六、还剩一项要你拍板（我没动）

**「剩余未收」在"没有合同"的客户上会显示负数。**

这张对账单的实测值：

```
合同金额 ¥0.00   本期已收 ¥120.00   →   剩余未收 −¥120.00
```

口径定义是 `剩余未收 = 合同金额 − 已收 − 预收核销`（界面右下角也写着这句）。
你们绝大多数业务走的是「订单 → 出库 → 开票 → 收款」，**库里没有合同**，
所以这一列对几乎所有客户都会是"−收款额"。

- 「期末应收」是对的（= 期初 + 已开票 − 已收 = 0），不含糊；
- 但「剩余未收 −120」看着像算错了。

我没有擅自改财务公式（封版前动口径风险太大）。可选三选一，你说了我就动：

1. **加下限 0**：`max(合同额 − 已收 − 核销, 0)` —— 多收的钱本就不属于"剩余未收"，改完最直观；
2. **只在有合同时才算**：合同金额为 0 时这一列显示「—」；
3. **保持现状**，只在表头补一句"仅统计合同口径"。
