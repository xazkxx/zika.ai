# 多文件智能识别上传 · 第一步（客户弹窗试点）— 2026-10-23

「新增客户 / 供应商 / 商品」三个弹窗最顶部的 **📄 智能识别上传（支持多选）** 区域。
本轮按约定**只接客户**跑通，供应商与商品等确认后再铺开（组件已是通用的，接线各 3 行）。

---

## 一、用户看到的样子

1. 点「新增客户」→ 弹窗顶部出现虚线框：
   `📄 智能识别上传（支持多选）` + 两个模式（**识别并填表** / **仅上传作为附件**）；
2. 点框选文件，或直接把文件**拖进去**（一次最多 6 个；JPG/PNG/BMP/WEBP/TIF、PDF、Word）；
3. 「识别并填表」→ 几秒后弹出 **「识别完成，请核对信息」**：
   * 每行一个字段，识别值用**黄色高亮**标出，下面一行小字是原文出处；
   * 有商品明细（报价单）时，另附一张明细表；
   * 认不出的项在黄色提醒里列出来（"没认出税号，请手动补"）；
   * 可以展开「看看读到的原文」自查；
4. 点 **应用到表单** → 逐项落到下面的输入框；点 **继续手填** → 一个字段都不动；
5. 「仅上传作为附件」→ 不识别，文件先挂在面板上，**点保存后**自动归档到该客户的附件库（分类=资质）。

> 刻意做成"先核对、后回填"：识别会错，直接写进表单用户就不看了。

## 二、后端

### 1. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/smart-upload/meta` | 支持的格式、每种档案允许的字段、上限 |
| POST | `/api/v1/smart-upload/parse` | multipart：`files`(多个) + `kind` + `mode` |

响应：

```json
{
  "kind": "customer",
  "mode": "parse",
  "files":   [{"name": "执照.png", "ok": true, "engine": "rapidocr", "chars": 174, "error": null, "preview": "…"}],
  "fields":  {"name": "陕西送变电工程有限公司", "tax_no": "91610103MA6TX8K23Q", "address": "…"},
  "evidence": {"name": "陕西送变电工程有限公司"},
  "field_labels": {"name": "名称"},
  "items":   [{"name": "电缆", "spec": "YJV-3x35", "unit": "米", "quantity": 100, "unit_price": 25.5}],
  "warnings": ["没认出纳税人识别号（开票、对账都要用），建议手动补上"],
  "elapsed_ms": 1639
}
```

### 2. 解析链（`app/services/smart_upload.py`）

| 格式 | 做法 | 备注 |
|---|---|---|
| 图片 | RapidOCR | **复用 `erp_invoice._ocr_image_bytes`**，同一套模型单例，不重复加载 |
| PDF | 先读内嵌文本层；无字才渲染前 3 页走 OCR | 扫描件最多渲 3 页，防 40 页合同吃内存 |
| .docx | python-docx：段落 + **表格** | 表格同时喂给明细解析器（`parse_docx_tables`） |
| .doc | olefile 抓 UTF-16LE 中文片段 | 尽力而为，质量不如 .docx |

### 3. 字段策略：正则、可解释、不猜

* **不猜**：认不出来就**不返回这个键**（而不是空串），靠 `warnings` 提示补录；
* **不覆盖**：多份文件合并时只补空缺（`_merge`）—— 第二份里"地址：见附件"不许盖掉第一份的完整地址；
* **不静默**：每个文件单独报 `ok/engine/chars/error`，一个坏了不影响其它；
* **可解释**：每个值都带 `evidence` 原文片段，核对弹窗直接展示。

## 三、踩到的四个坑（都写进注释和测试了）

1. **「名　称」被 OCR 拆行**：实测识别成 `名和\n称陕西送变电工程有限公司`，
   公司名前面挂了孤零零一个「称」。→ `_tidy_name()` 只剥「称/名/所/址/话」这几个标签碎片，
   **不动 和/华/中**（"和平商贸有限公司"剥掉"和"就毁了），且剥完还得像公司名才动手。
2. **税号里凑出假手机号**：`9144030071526726X9` 里能划出 `14403007152`，正好匹配 `1[3-9]\d{9}`。
   → 认电话前先把税号和 15 位以上长数字串抹掉。
3. **Word 表头被当成公司名**：摊平后的表头是「产品名称 | 规格型号 | …」，
   按"名称"去搜会命中它。→ 标签前加 `(?<![\u4e00-\u9fa5])`（前面不能是汉字），
   且值里带 `" | "` 一律判定为表格行、丢弃。
4. **「供应商：XX公司」整行**：没有「名称:」标签时走"猜最长公司名"，会把标签一起带进来。
   → 猜之前先切掉行首的 `xx：` 前缀。

## 四、前端

`frontend/src/components/partners/SmartUploadPanel.jsx`（新，通用组件，`kind` 决定字段集）
+ `smartUpload.css`（新）。

* 挂在 `PartnerModal` 的 `<form>` 最顶部，**只在新增态显示**
  （编辑态用新执照覆盖历史档案的名字/税号是危险的）；
* 面板自己发请求、自己做核对弹窗，只通过 `onSmartFill(fields)` / `onSmartFiles(files)`
  往回传结果 —— `PartnerModal` "不持有业务状态"的约定没被破坏；
* 按钮全部 `type="button"`：在 `<form>` 里，默认按钮会在点「识别」时把整个档案表单提交掉；
* 核对弹窗 `z-index: 1100`，必须高于 `.modal-backdrop` 的 1010，否则被父弹窗盖住点不到。

App.jsx 侧：
* `applyCustomerSmartFill(fields)` → `setCustomerForm(prev => ({...prev, ...fields}))`；
* `customerSmartFiles` 暂存「仅上传作为附件」的文件，**客户创建成功后**逐个 POST 到
  `/customers/{id}/files`（分类=资质），部分失败只提示"归档 x/y 个"，不让整单保存变红。

## 第二步（2026-10-23 晚）：铺开到供应商 + 商品

第一步只接了客户，跑通后按约定铺开剩下两个入口。

### 1. 供应商

完全复用客户那一套：`<PartnerModal kind="supplier" smartUpload onSmartFill={applySupplierSmartFill}>`，
后端 `parse_party_fields(text, "supplier")` 本来就支持（税号/开户行/账号/手机/座机）。
**没有「仅上传作为附件」这一路** —— 供应商没有附件库，硬做会留下无主文件。

### 2. 商品（新增 `parse_product_fields`）

商品资料/报价单和"公司抬头"文档形态完全不同，单独一个解析器：

| 字段（前端 key） | 来源标签 |
|---|---|
| `name` | 产品名称 / 商品名称 / 品名 / 物料名称；都没有就取第一行"像商品名"的短行（跳过"报价单/产品资料/目录"这类标题） |
| `standards`（规格） | 规格型号 / 规格 / 尺寸 |
| `brand`（型号） | 型号 |
| `unit` | 单位 / 计量单位 |
| `sale_price` | 销售价 / 零售价 / 报价 / 单价（`¥1,280.00` 会洗成 `1280.00`） |
| `purchase_price` | 采购价 / 成本价 / 进价 |
| `tax_rate` | 税率 13% → `13` |
| `manufacturer` | 生产厂家 / 生产商 / 制造商 / 厂家 / 品牌 |

**报价单兜底**：抬头没写产品名、明细全在表格里时，用识别到的**第一行明细**补
`name / standards / unit / sale_price`。

### 3. 明细逐行取用（商品专有）

核对框里的明细表多了一列「用这一行」（`data-su-item`）：
点哪行就把 `名称/规格/单位/销售价` 填成那一行。报价单通常有多行，
让用户挑一行比让他抄快得多，也不用先保存再改。

### 4. 顺带补的可用性

`ProductEditModal` 的所有输入框加了 `data-product-field={key}` 锚点 ——
商品弹窗以前没有任何字段级钩子，自动化只能按"第几个 input"数，字段顺序一变全错。
