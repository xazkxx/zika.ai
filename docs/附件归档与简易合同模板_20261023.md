## 一、附件归档（系统设置 → 公司信息页底部）

### 1. 解决什么问题

附件（合同原件、付款回单、模板、发票扫描件、客户资料、商品图片）散在 `data/` 的 6 个子目录里。
以前没人回答得了三个问题：**到底占了多少、还剩多少、怎么整体拷走**。现在一页看完，一键打包。

### 2. 三个口径（写死了，别改）

| 口径 | 做法 | 为什么 |
|---|---|---|
| 只统计白名单目录 | `ATTACHMENT_DIRS` 六项 | `data/` 里还有导出的库、日志；一起算会让用户以为"附件占了 20G" |
| 备份里排除 `backups/` 自身 | 显式 `rglob` 白名单，不用 `make_archive` | 否则备份套备份，点一次体积翻一倍 |
| 磁盘剩余按 data 所在分区算 | `shutil.disk_usage(root)` | 换盘符也不会算错 |

### 3. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/system/attachment-storage` | `dirs[] / total_files / total_bytes / disk{total,used,free} / backups[] / root / backup_dir` |
| POST | `/api/v1/system/attachment-backup` | 在 `data/backups/` 生成 `附件备份_yyyymmdd_HHMMSS.zip`，返回 `name/bytes/files/message` |
| GET | `/api/v1/system/attachment-backup/{name}` | 默认流式下载；`?as=base64` 走 JSON 通道（见下） |

### 4. ⚠️ 踩到的坑：Chrome 把 `.zip` 直链的 fetch 吃成空 204

第一版前端是标准的 `fetch → blob → a.click()`。验收时出现 **用户点「下载」只得到一个 0 字节的 zip**。

排查结论（隔离测试，与业务代码无关）：

```
同一条 URL：
  curl                     → 200, 19747394 字节
  Chrome fetch             → 204, body 0 字节, 连 content-type 都没有
  Chrome fetch + Range 头  → 200, 19747394 字节（全量）
  同一站点的 CSV 导出      → 200, 266 字节（正常）
  内联 PNG（inline 处置）  → 200, 70 字节（正常）
有头 Chrome / 无头 Chrome 表现一致
```

即：**浏览器对"压缩包类下载"有拦截策略，直链 fetch 拿不到 body**。
处理方式与打印 PDF 完全一致 —— **不要指望二进制直链，改走 base64 塞进 JSON**：

* 后端 `?as=base64` → `{filename, bytes, content_base64}`；
* 前端 `atob` → `Uint8Array` → `Blob` → `a.download`，并加三道兜底：
  `bytes.length === 0` 报"服务端返回空包"、长度与 `bytes` 不一致报"下载不完整"、成功后给明确提示；
* 200MB 以上的包不做 base64（字符串化会顶爆浏览器内存），直接 413 并把用户指到 `data/backups/`。

### 5. 前端

`frontend/src/pages/SettingsPage.jsx` 新增 `<section data-attachment-storage>`：

* 三张汇总卡：附件总占用 / 存放位置 / 磁盘剩余（长路径用 `direction: rtl` 让省略号落在左边，保住末级目录名）；
* 目录占用表：目录 / 用途 / 文件数 / 占用，6 行固定（空目录也显示 0，避免"少了几个目录"的错觉）；
* 操作区：「一键备份所有附件」+ 刷新 + 结果提示；
* 最近备份表：包名 / 生成时间 / 大小 / 下载（最多显示 5 条，多了一律滚动）。

样式全部收在 `styles.css` 末尾的 `storage-*` 块里，`table-layout: fixed` + 明确列宽，长名字 ellipsis 收口。

## 二、内置合同模板换成《产品买卖合同（简易版）》

### 1. 为什么换

客户实际在用的就是这一份（源文件是 WPS 的 `.wps`，用 `olefile` 取 UTF-16LE 文本核对过措辞）。
原来的《工矿产品购销合同》条款更细，但**口径不一样**，直接拿来签会和客户习惯冲突：

| 条款 | 简易版（新默认） | 详细版（保留） |
|---|---|---|
| 结算 | **款到发货** | 验收后 30 日内 |
| 违约 | **固定 20% 合同金额** | 按日万分之五累计 |
| 争议 | **施工所在地法院** | 签订地法院 |
| 份数 | **一式 4 份，各执 2 份** | 一式 2 份 |

### 2. 两个变体怎么切

`app/services/contract_template.py`：

```python
TEMPLATE_SIMPLE = "simple"   # 默认，《产品买卖合同（简易版）》
TEMPLATE_DETAIL = "detail"   # 《工矿产品购销合同》
build_gongkuang_document(payload, items=None, template=None)
# template 不传 → 看 payload["template"] → 再不行用 simple
```

所以 HTTP 层不用长参数：请求体里塞 `{"template": "detail"}` 就切回详细版。
预览、PDF、Word 变量替换三条链路共用同一套结构，换的只是条款口径。

### 3. 跟着改的地方

* `document_to_print_spec()` 的副标题不再写死「工矿产品购销合同」，改成跟着 `template_name` 走；
* 导出 PDF 的文件名 `gongkuang_xxx.pdf` → `contract_xxx.pdf`（存到硬盘上要对得上用户看到的那份）；
* 界面文案：录入区下拉的"不使用模板（系统内置《…》）"、两个按钮的 `title`、台账组件提示；
* 前端不再需要选模板类型：默认就是简易版。
