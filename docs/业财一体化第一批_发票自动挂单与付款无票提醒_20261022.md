## 一、发票自动匹配（后端）

### 设计取舍：只自动挂"有把握的那部分"

模型注释里当初写着"不自动匹配"，理由是一票多单 / 一单多票猜不准 —— **这个判断今天仍然成立**。
所以这套逻辑不是"尽量都挂上"，而是：

> **只有"唯一强证据"成立时才写库，其余一律返回候选让人点。**

自动落库三个条件，缺一不可：

1. **金额一致**：发票价税合计 == 单据净额（`total_amount - discount_amount`），容差 0.01；
2. **余量够**：该单未开票余额 ≥ 本票金额（不制造"超开票"，否则完结闸会被骗过去）；
3. **唯一**：满足前两条的候选恰好 1 张。

其余情况返回 `ambiguous`（有候选，请人点）或 `none`（人工兜底）。

三条硬规矩：

- **绝不覆盖人工**：`related_order_id` 已有值 → 直接 `skipped`；
- **红字票不猜**：冲红票必须和它冲的那张蓝票挂同一张单，只有开票人知道是哪张；
- **只认出库单 / 入库单**：完结闸和钱票两清算的就是这两张单，挂到"订单"上等于挂了个不参与结算的壳。

### 核心函数（摘要）

```python
# app/services/invoice_match.py

def order_invoiced_amount(db, order_id) -> float:
    """该单已挂发票的价税合计（红字票是负数，天然抵扣）。
    与 erp_sales.py 完结闸那段 SQL 逐字等价 —— 唯一口径。"""
    total = db.query(func.coalesce(func.sum(Invoice.total_amount), 0)) \
              .filter(Invoice.related_order_id == order_id).scalar()
    return round(float(total or 0.0), 2)


def order_uninvoiced_amount(db, order) -> float:
    """未开票 = max(总额 − 已开票, 0)。
    ⚠️ 用总额不用净额：必须和完结闸对齐，否则用户看到"提醒差 100、完结说差 0"。"""
    return round(max(0.0, float(order.total_amount or 0) - order_invoiced_amount(db, order.id)), 2)


def match_invoice(db, invoice) -> MatchOutcome:
    """算一次匹配，纯读不写。"""
    if invoice.related_order_id:      return skipped("已经挂过单据，不自动改")
    if invoice.direction not in ("input", "output"): return skipped("方向待判定")
    if (invoice.invoice_flag or "blue") == "red":    return skipped("红字票请手工指定冲红对象")

    party_id, party_name, label = _resolve_party(db, invoice)   # 销项→客户档案；进项→供应商
    if not party_id:                  return none("抬头没对上档案…")

    pool = _collect_candidates(db, invoice, party_id, party_name)   # 日期窗口内、未作废
    strong = [c for c in pool if c.amount_equal and c.balance_enough]

    if len(strong) == 1:   return matched(strong[0])        # ← 只有这一条会落库
    if len(strong) > 1:    return ambiguous("有 N 张单金额都对得上，必须人工指定")
    return ambiguous("没有金额完全一致的单据，以下是按日期/单号线索排出的候选")


def auto_attach(db, invoice) -> MatchOutcome:
    """建票/上传后的收尾动作。**匹配失败绝不拖垮开票主流程**。"""
    try:
        outcome = match_invoice(db, invoice)
        if outcome.status == "matched":
            return apply_match(db, invoice, outcome.order_id, source="auto")
        return outcome
    except Exception as exc:
        return skipped(f"自动匹配跳过（{type(exc).__name__}: {exc}）")
```

`apply_match()` 是**唯一**写 `related_order_id` 的入口，多两道校验：
方向必须对（销项只能挂销售单）、往来单位必须一致（跨对方的挂单 100% 是错的，直接 `ValueError` → 409）。

## 二、采购付款无票强提醒（前端）

### 为什么是"闸"而不是"toast"

业务规则是"先款后票"，但"这笔付款没有票"在账上是**看不见**的 —— 结果要么忘了催票，
要么年底汇算才发现缺票。toast 会被当成"保存成功"的反馈，点完就走；
所以这里做成**打断式闸门**：点「确认付款」不提交，切到警告面板，逼你三选一。

### 三道防线

1. **打开弹窗就告诉你有票没票**：标题右侧角标「进项票缺 ¥200.00」/「进项票已齐」；
2. **点之前先示警**：表单里黄字"本单还有 ¥x 未取得进项发票。点『确认付款』会先让你选择…"；
3. **点下去被拦住**：警告面板，三个出口，**没有默认焦点**、不接受回车直过：

```
! 此笔付款暂无发票
  请及时索取发票，或做暂估处理。
  ┌──────────┬──────────────┬──────────┐
  │ 本单应付  │ 已挂进项票    │ 还差票    │
  │ ¥200.00  │ ¥0.00（0 张）│ ¥200.00  │
  └──────────┴──────────────┴──────────┘
  [先去索取发票] [做暂估处理并付款] [仍然付款（不记票）]
```

两个"继续"出口都会在流水备注打标（后端落，不能只靠前端）：
`【暂估】付款登记：…` / `【无票付款】付款登记：…`。
